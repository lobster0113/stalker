# ADR 0019 (제안): 실전 규칙 학습 계획 — 사이즈·스택·인원·토너먼트·TP key

- 상태: **제안**. 예산: NH-9(월 $300 승인) 뒤 #387 측정으로 다시 물었고, NH-10(2026-10-30)에서 월 $100 유지로 정했다(§5). 학습 순서·R0/R1·C 착수 조건은 R0 결과 뒤 "채택"으로 바꾼다.
- 이슈: #390. 대상: #382(PR #388, 실전 사이즈), #383(스택), #384(인원 2–6), #385(토너먼트·앤티·ICM), #389(TP key 보강). 관련: #386(웹 real 메뉴), #387(real 메뉴 CI 비용), #373(cpu5c), #339(tp6 비용).
- 개정: 2026-10-30 외부 설계 리뷰 반영(#420, `docs/research/2026-10-30-design-review-intake.md`). R0·R1 승인 단계(§3.1), C 착수 조건(§3.4), D·E의 환경별 후회값과 warm start 비교(§3.2), 상태 용어(§7)를 더했다.
- 대체: ADR 0017의 학습 순서·비용 계획. ADR 0017 §8의 파드 실측은 이 문서의 입력으로 그대로 쓴다.

## 1. 결정 (소유자, 2026-10-30) — 고정
- 학습·AI·채점의 규칙은 실전과 같아야 한다. **실전성을 연산 비용과 바꾸지 않는다.** 예산이 모자라면 범위를 줄이지 않고 돈이나 시간을 더 쓴다.
- 실전 사이즈: #382 코멘트의 목록 전부(프리플랍 오픈 2–10BB 10종, 3bet 2.5–5배, 4bet 2–3배, 5bet+ 올인, 포스트플랍 벳 pot 20–300% 8종, 레이즈 2.5–10배 6종, 올인). 구현은 PR #388의 `real` 메뉴.
- 좌석마다 다른 스택(사이드팟 포함). **모든 플레이어의 유효 스택과 SPR**이 TP의 공개 사실이다(#383 마지막 소유자 코멘트).
- 인원 2–6인(#384). 토너먼트는 앤티 있음·없음, ICM 포함(#385).
- TP key는 TP 판단과 사실을 쓴다(#389). **드로우(플러시·백도어 플러시 포함, 무늬 인식 `hand.outs`·`hand.vuln`)와 블로커(새 TP 항목 `hand.block`)는 예외 없이 정책에 들어간다**(#389 소유자 코멘트, 2026-10-30). 비용 때문에 빼지 않는다. 이 계획이 그 비용을 예산에 넣는다.
- 지금 서비스의 v1 메뉴 중수·고수 정책은 **임시본**이다. v1 파드 체인은 멈춘다(더 돌린 반복은 버려진다).

## 2. 결론 (추천)
- **전체 체인은 한 번만, "실전 캐시 결합 key"에서 돌린다.** 그 전 단계(#388 메뉴, #389 key 항목, #383 스택)는 모두 key를 바꾸므로, 단계마다 짧은 측정 run만 한다. 측정은 무료 CI 10⁵회와 90분 파드 1–2회다.
- 결합 key를 정할 때 **#384·#385가 쓸 칸을 미리 넣는다**(인원 수, 버튼 기준 포지션 이름, 앤티 여부, 토너먼트 단계). 칸을 예약해도 새 인원·토너먼트 key는 C에서 방문되지 않으므로 C의 후회값이 그 key로 옮겨 가지는 않는다. 그래서 D·E는 **엔진·특징 코드를 공유하고 후회값은 환경별로 둔다.** C 정책을 출발점(warm start)으로 쓸지는 cold start와 같은 연산으로 비교해 정한다(§3.2, #384·#385).
- **C 전체 체인 전에 R0·R1 승인 단계를 거친다**(§3.1, §3.4). key 충돌 EV 손실(#410), 레인지 고정점(#411), 후회값 갱신 산술 오라클(#414), 림프 원인(#391), 규칙 교차 검사(#412), 강한 공격자 평가(#413)가 대상이다. 같은 key가 묶으면 안 되는 상태를 묶거나 갱신 식이 틀리면, 연산을 늘려도 잘못된 정책을 더 정밀하게 배울 뿐이기 때문이다.
- 비용 갱신(2026-10-31, #400): 결합 key `c1`을 확정하고 X를 B1·B3 CI 측정으로 다시 잡았다(§4.2). 실전 캐시 6인 중수+고수 결합 체인은 **$432–2,283, 중간값 약 $1,007**, 2–6인·토너먼트까지 합친 전체는 **약 $1,105 / $4,056 / $16,020**이다. 고수 체인 중간값 $631은 중단 규칙 기준 $660 아래다(§5). 아래 줄은 이전(10-30) 값이다.
- 비용(측정값 × 표기한 배수 가정, §4): 실전 캐시 6인의 중수+고수 결합 체인은 **$305–1,671, 중간값 약 $702**이다. 2–6인과 토너먼트까지 합친 전체는 측정 run을 더해 **$788–11,738, 중간값 약 $2,836**이다. 드로우·블로커 항목(필수)의 키 배수를 넣은 값이다. 2026-10-30 real 메뉴 CI 측정(#387)으로 K·T를 바꿨다. 이전 추정은 $312 / $1,600 / $9,705였다. 범위가 넓은 이유는 결합 key 배수 X가 아직 측정되지 않았기 때문이다. 단계별 측정 run(합계 약 $25–40)이 이 범위를 좁힌다.
- 예산: #387 측정 뒤 중간값 $2,836. 소유자 결정(NH-10, 2026-10-30): 지금 상한 월 $100 안에서 진행하고, 상한에 닿으면 로컬 CPU 장비 사양·비용을 산정해 다시 정한다(#427). 월 $300 구현(#406)은 보류. 범위는 줄이지 않는다(§5).
- 용량: cpu3c 용량 부족(HTTP 500)과 호스트별 2.2배 처리량 차이가 체인 벽시계를 정한다. launcher에 **flavor 대체 목록, 용량 오류 시 지연 재시도, 느린 호스트 조기 재발급**을 넣자(§6, harness-change 후속).

- B1은 결과가 어떻든 결합 key에 들어간다. 측정은 비용을 재고 버킷 경계를 정하는 데만 쓴다. 넣을지 말지를 정하는 데는 쓰지 않는다. B2·B3도 #389 수용 기준이라 같은 방식이다.
- B1–B3와 S는 서로 독립이라 병렬로 구현할 수 있다. 둘 다 key를 바꾸므로 각각 "그 항목 없는 key"와 같은 반복으로 비교한다(#389 기준). B2·B3는 B1 위에서 잰다. 그래야 결합 key의 항목 수가 측정 순서와 맞는다.
- #386(웹 엔진 real 메뉴)은 A 직후 B·S와 병렬로 한다. 서비스의 사이즈 입력과 번역이 임시 정책에도 필요하기 때문이다(§7).
- 사용자 제안과 다른 점은 하나다. C에서 key 스키마를 확정할 때 D·E용 칸을 미리 넣는다. 지금 key의 `seat`는 6인 좌석 번호라 인원이 바뀌면 의미가 달라진다. 버튼 기준 포지션 이름(BTN·SB·BB·UTG…)과 인원 수를 C에서 key에 넣으면, D는 새 딜 모양만 더한다.

### 3.2 재학습을 강제하는 것 / 공유하는 것
| 변경 | 기존 key의 의미가 바뀌나 | 기존 체인 재사용 |
|---|---|---|
| A 메뉴 v1 → real | 예(액션 라벨·합법 액션·트리 전부) | 불가 — v1 체인은 버린다 |
| B1–B3 key 항목 추가 | 예(key 문자열이 갈라진다) | 불가 |
| S 균등 100BB → 좌석별 스택 | 예(스택 칸이 없는 key는 여러 깊이를 섞는다) | 불가 |
| C 결합 key | — | **첫 전체 체인** |
| D 2–5인 추가 | 아니오(인원 수·포지션 이름 칸이 C에 있으면 6인 key는 그대로) | 6인 key는 그대로 쓴다. 2–5인 key는 C에서 방문되지 않았으므로 후회값이 0에서 시작한다. C 평균 정책을 prior로 쓸지는 A/B(#384) |
| E 앤티·ICM | 아니오(앤티 여부·토너먼트 단계 칸이 C에 있으면 캐시 key(단계 = 캐시, 앤티 없음)는 그대로) | 보상(상금 EV)이 달라 캐시 후회값은 옮기지 않는다. 엔진·특징·레인지 코드만 공유. warm start는 A/B(#385) |

- 그래서 A·B·S는 **한 번의 재학습(C)을 공유한다.** v1이나 중간 단계 key로 전체 고수 체인을 돌리면 그 돈은 버려진다.
- D·E가 재학습을 강제하는 경우는 하나뿐이다. 측정 run이 예약한 칸으로 모자란다고 보이면(예: 헤즈업에 다른 버킷이 필요) key가 바뀐다. 그때는 그 단계 앞에서 C를 다시 연다. 이 위험을 줄이려고 D·E의 첫 측정 run(파드 90분)을 C 전체 체인 **전에** 돌린다. C 체인에 쓰는 결합 key 코드로 2–5인·토너먼트 딜을 짧게 돌려 키 분포와 LBR이 정상인지만 본다.
- 칸 예약의 근거: 정보 집합(key)마다 후회값이 따로 쌓인다. 새 딜 모양이 기존 key에 닿지 않으면 기존 key의 갱신 식은 바뀌지 않는다. 그래서 6인 캐시 key는 D·E에서 다시 학습하지 않아도 된다. 다만 **새 key에는 C의 정보가 쌓여 있지 않다.** "이어 학습"은 6인 캐시 부분을 버리지 않는다는 뜻이지, 새 환경 학습이 공짜라는 뜻이 아니다. §4의 D·E 비용이 그 학습이다. 토너먼트는 목적함수(상금 EV)가 달라, 같은 공개 상황이라도 캐시 key와 같은 key를 쓰면 안 된다(CHARTER 환경 분리).

### 3.3 단계별 측정 run (전체 체인 전)
- **CI 10⁵회(무료)**: `train.yml` 4코어 잡, 시드 4. 키 수·it/s·LBR·메뉴 밖 LBR·필드를 그 항목 없는 key와 비교한다(#389 기준). 주의: real 메뉴 10⁵회는 `train.yml` 잡 상한 340분에 가까울 수 있다. tp6가 15,213초(254분)였고 real은 로컬에서 tp6보다 1.4배 느렸다(PR #388, 참고값). 그래서 약 355분으로 추정한다. run 40971384338은 시드 2–4가 상한에 걸렸다. **이후 real 메뉴 CI 측정은 5×10⁴회로 하거나 이어 달리기 두 조각으로 나눈다.**
- **파드 90분 1–2회(회당 약 $1.5–1.7, ADR 0017 §8의 실측 비용)**: 같은 시간에서 LBR을 비교한다. #339 노트가 권한 "같은 비용 비교"다.
- 전체 체인(10⁶–10⁷회)은 C에서만 돌린다. 파드는 이어 달리기(#354)를 쓴다.

### 3.4 C 전체 체인 착수 조건 (go/no-go)
모두 통과해야 C 고수·중수 전체 체인을 디스패치한다. 하나라도 못 하면 그 이유와 다음 측정을 이슈에 적고 기다린다.
- [ ] 규칙: 메뉴 밖 금액·min-raise·언더레이즈 올인 재오픈·5bet+ 비올인·사이드팟 전이가 PokerKit와 일치(#412, #383).
- [ ] key 충돌: EV 손실 상위 충돌이 보고되고, 결합 key가 그중 큰 것을 가르거나 남긴 이유를 적었다(#410).

### 4.2 계산식과 가정
- 비용(등급) = v1 체인 비용(등급) × K × T × X
  - **K** = real 메뉴의 키 배수. **가정: 같은 LBR에 필요한 반복은 키 수에 비례한다.** v1 실측으로 중수는 키당 30회, 고수는 키당 15회에 지금 LBR에 닿았다.
  - **T** = real 메뉴의 반복당 시간 배수.
  - **X** = 결합 key(B1–B3 + S)의 추가 키 배수. **측정값 없음.** 범위는 가정이고, 측정 run으로 바꾼다.

  - K = **2.18**(측정, #387). 10⁵회에서 키가 아직 늘고 있어 더 커질 수 있다. 이전 가정 1.3 / 1.6 / 2.0은 측정보다 낮았다.
  - T = 3.65 / 4.2 / 5.0. 근거: 낮음은 끝난 시드 1의 측정값이다. 이전 판처럼 학습 초(train seconds)의 비로 잰다. 결과 JSON의 평균 it/s 비(22.66 / 5.71 = 3.97)는 v1 쪽 평균에 다른 러너가 섞여 있어 쓰지 않았다. it/s 기준이면 낮음이 약 4.0이 된다. 나머지 세 러너는 340분 안에 끝나지 못해 T가 약 4.1 이상이다. 그래서 중간을 4.2, 높음을 5.0으로 잡았다(CI 러너 편차, 파드 처리량 비율은 v1과 같다고 **가정**).

- **중단 규칙**: C 측정 run 뒤(또는 그 전이라도 추정이 넘으면) 결합 key 고수 체인 추정이 직전 중간값의 1.5배를 넘으면, 고수 전체 체인을 디스패치하기 전에 NEEDS_HUMAN에 새 수치로 묻는다. 2026-10-30 #387 측정에서 $246 → $440으로 넘었고, NH-10으로 물어 위 결정을 받았다. 다음 기준은 $440 × 1.5 = $660이다. 범위는 줄이지 않는다(드로우·블로커 포함). 묻는 것은 돈과 일정이다.
- 상한을 바꾸려면 `harness/budget.json` 수정(harness-change)이 필요하다. 사용자 승인 뒤 Planner가 그 이슈를 만든다.

## 6. 용량과 호스트 편차
- 실측: cpu3c 32 vCPU 파드 생성이 2026-10-29 19:45Z와 약 20:50Z에 HTTP 500 "There are no longer any instances available with the requested specifications"로 실패했다(run 40942964043·40942970483·40952827318·40952833261, 비용 $0). STATE 경보 기준으로 20:52–21:20Z에도 6연속 실패했다.
- 실측: 같은 cpu3c($0.96/h)가 EPYC 9655·9654·9754·7713 호스트에 떨어진다. it/s는 67.7–151로 **2.2배** 차이다(#373). 느린 호스트에 걸리면 같은 돈으로 반복을 절반만 산다. 결합 key 고수 체인 약 83회에서는 이 편차가 수십–200달러 단위다(느린 호스트 비율에 따라, 중간값 $440 기준).
- 실측(#373, `docs/research/2026-10-e3-cpu-flavor.md`): cpu5c 32 vCPU는 $1.12/h에 두 번 다 EPYC 9575F로 떨어졌고 중수 9인 161 it/s, **반복/$가 cpu3c 같은 잡 평균의 1.55배**(빠른 9655 호스트보다도 1.17배)다. 두 번 다 용량 오류 없이 만들어졌다.
- 제안(harness-change 후속 ②, `harness/cloud/launcher.py`):
  1. **flavor 대체 목록.** 잡 명세에 `cpu_flavors: [..]`(순서 있음)를 허용한다. RunPod `cpuFlavorIds`에 목록을 그대로 넘기거나, 용량 오류 때 다음 flavor로 다시 만든다. 순서는 #373의 it/s per $ 측정으로 정한다(cpu5c가 이기면 cpu5c 먼저). flavor마다 `hourly_usd` 상한을 둬 기존 요금 검사가 비싼 파드를 멈추게 한다. vCPU는 32로 고정한다. 그래야 병렬 MCCFR 워커 수와 체크포인트가 이어진다.
  2. **용량 오류 지연 재시도.** HTTP 500 no-instances는 비용이 0이다. 15·30·60분 간격으로 최대 몇 회 재시도하고, 실패하면 journal·이슈에 남긴다. 지금은 run이 실패로 끝나고 다음 디스패치까지 체인이 쉰다.
  3. **느린 호스트 조기 재발급.** 파드 시작 직후 `machine.cpu_model`과 첫 진행 줄의 it/s를 본다. 잡의 실측 중앙값의 0.6배 미만(예: 9754 67.7, 7713 71.2 it/s)이면 한 번만 종료하고 다시 만든다. 10분 비용(약 $0.16)으로 반복이 절반인 run(회당 약 $4–5)을 피한다.
- 이 셋이 없어도 계획은 진행된다. 그러면 §4의 벽시계에 용량 대기와 느린 호스트 run이 더해진다.

## 7. 새 정책이 나올 때까지 서비스가 보여 주는 것
- 중수·고수(`web/app/policy/mid-6.json`·`pro-6.json`)와 초보(`beginner-6.json`)는 지금 v1 정책을 그대로 쓴다. 대신 **임시본임을 화면에 표시한다.** 예: "임시 AI: 학습 사이즈 오픈 2.5BB·레이즈 3배·벳 33/75%, 100BB 균등 스택, 6인 캐시 전용. 실전 규칙 정책 학습 중". `index.json`에 `placeholder: true`와 규칙 설명을 넣어 화면이 그것을 읽게 한다.
- 히어로는 실전 사이즈를 모두 쓸 수 있다(#386). 임시 정책의 AI와 채점은 그 사이즈를 정책 메뉴의 이웃 사이즈로 번역해 읽는다(TP.md §6 의사 조화 번역). 채점 화면에 "임시 정책 기준"을 붙인다.
- 정책이 덮지 않는 상황(6인이 아닌 인원, 100BB에서 먼 스택이나 좌석별로 다른 스택, 토너먼트)은 지금처럼 규칙 봇으로 하고 **"미학습(규칙 봇)"**으로 표시한다. 학습된 AI처럼 보이게 하지 않는다.
- 교체: 결합 key 체인이 등급별 목표(§4.2)에 닿으면 `export_web_policy`로 내보내고 Gate U를 통과한 뒤 그 등급의 임시 표시를 뗀다. D·E 이어 학습이 끝나면 인원·토너먼트 상황의 "미학습" 표시를 뗀다.
- 상태 용어: 기능·정책을 말할 때 **구현됨(PR) / 머지됨 / 배포됨(서비스에 반영) / 정책 학습됨(그 규칙으로 학습한 정책이 서비스에 있음)**을 구분한다. 예: real 사이즈 입력은 머지·배포됐지만 real 메뉴로 정책 학습은 되지 않았다.
- 메뉴 밖 사이즈를 번역해 채점할 때 번역 오차가 큰 경우는 "근사(번역)"로 표시하고 만점 판정을 하지 않는다(#417).
- 공개 출시는 NH-7(ADR 0018) 결정을 따른다. 임시본을 공개 서비스의 기본으로 두지 않는다.
