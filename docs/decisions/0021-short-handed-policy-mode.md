### (b) 인원별 정책 — **측정 없음**
`ops`에 인원별(2·3·4·5인 단독) c1 학습 결과가 없다. 6인 단독 c1만 있다:
- C6(`training/e3-tp-mid-c1-w4/41434060242.json`): 20,000회, `iters_per_s_mean` 2.72(CI w4), `infosets_by_seed` 380,911 / 383,854 / 379,094 / 377,746, `lbr_bb_by_seed` 1.869 / 1.799 / 1.185 / 1.598(평균 1.613), `lbr_average_bb_by_seed` 1.444 / 1.718 / 1.246 / 1.943.
- C6은 CI 러너 w4이고 M2–M4는 파드 w16이라 it/s를 직접 비교하지 않는다. 6인 학습 핸드도 20,000 대 약 8,000으로 다르다. 6인 LBR은 두 쪽이 서로의 se 범위 안이다(1.613 대 1.940 ± 0.460).
- 2–5인 단독 정책의 키 수·it/s·LBR은 **측정 없음**.

## 선택지
- **(a) mixn c1 한 정책.** 파일·체크포인트·체인이 하나다. 키가 인원별로 갈라지므로(공유 0.04%) 표 해상도에서 (b)보다 잃는 것이 없다. 단점: 인원별 연산 배분이 혼합 비율(지금 균등)에 묶인다. 6인은 40,000회 중 약 8,000핸드만 본다.
- **(b) 인원별 정책 5개.** 인원마다 반복 수를 따로 줄 수 있다. 단점: 체인·체크포인트·평가·내보내기가 5배이고, 공유 키 약 510개를 인원마다 따로 학습한다. 표 분리라는 이점은 c1 key가 이미 준다. 측정이 없다.
- **(c) 측정 후 결정(보류).** (b)를 같은 연산으로 재 본 뒤 정한다. #384가 막힌 채 남는다.

## 결정 1: 정책 방식 — (a) mixn c1 한 정책
**(a)를 채택한다.** 이유:
1. 측정이 있는 쪽은 (a)뿐이고, 2–6인 모두 ADR 0020 퇴행 방지선을 통과한다.
2. 인원 사이 공유 키가 0.04%라 (a)는 구조적으로 "인원별 표의 묶음"이다. (b)가 더 줄 수 있는 것은 표 분리가 아니라 **인원별 연산 배분**뿐이다.
3. 운영 비용: (b)는 체인·평가·아티팩트·`index.json` 항목이 5배다. (a)는 #541의 `by_players` 조회에 한 정책에서 인원별로 내보내면 된다.

다시 여는 조건(하나라도 해당하면 (b) 측정 이슈를 연다):
- 이어 학습 중 어떤 인원이 ADR 0020 선을 넘는데 다른 인원은 통과해, 혼합 비율로 연산을 옮길 필요가 보일 때.
- 체인 메모리가 파드 한도에 닿아(연구 노트 「메모리」, 16 워커 약 40GB / 64GB) 표를 인원별로 나눠야 할 때.

(b) 측정 후속 후보(지금은 열지 않는다, Planner 판단):

| 예상 비용 | run당 약 $0.4–0.8(추정: M2–M4 실비 $1.45–1.87의 학습 몫을 1/5로, 평가 몫은 한 인원만), 6 run 약 $2.4–4.8. 디스패치/기록 2회 실행 전제(STATE 경보 (e)) |

## 결정 2: 9인 모델(mid9, run 40901138581) — 이 작업에서 연결하지 않는다, 후속으로
- 사실: 40901138581은 `e3-tp-mid9-pod32`의 이어 달리기 run이다(`budget/ledger.jsonl` 15–16줄: start 10-29 15:24Z, end exit 0, $1.6064, `result_bytes` 5,931,425). 결과 요약이 `ops:cloud/results/`에 **없다**(그 디렉터리에 40901138581 파일 없음). 9인 CI 기록은 `training/e3-tp-mid9-w4/40809731750.json`·`40831791990.json`(25만 회, `lbr_bb_mean` 0.572)뿐이다.
- 그 run은 ADR 0019(10-30) 이전 커밋 bc819f8(`docs/research/2026-10-e3-cpu-flavor.md` 표)에서 돌았다. 실전 메뉴(#382)·좌석별 스택(#383)·c1 key(#400, 11-01 머지)가 들어가기 전 형식이다. 서비스가 지금 6인에 쓰는 정책도 같은 세대이고 `index.json`에 `placeholder: true`로 표시돼 있다. 9인을 이 세대로 붙이면 곧 버릴 형식에 웹 key 미러·Gate U를 한 번 더 만든다.
- **결정**: 연결하지 않는다. 9인은 c1 key의 인원 칸으로 학습한다(`--player-mix`에 9를 넣거나 9인 단독, ADR 0019 순서상 D 체인 뒤). 그 전까지 9인 테이블은 지금처럼 학습 정책 없이 대체 동작을 쓴다.
- 후속 후보: 「c1 9인 첫 측정 파드 run(시드 2–4, 40k, `by_players["9"]`) + 9인 포지션 이름 칸 확인」. 9인 평가 합격선은 그 측정 뒤 ADR 0020 방식으로 정한다.

## 후속 (Planner 이슈화 후보)
1. 웹 c1 key 미러: `web/app/tpgto.js`가 c1 key(인원 칸·포지션 이름)를 만들고 Python과 패리티 벡터(2·4·6인)로 맞춘다. 지금 웹 key는 c1 이전 형식이다.
2. mixn c1 정책 내보내기: M2–M4 중 하나(또는 이어 학습 끝 run)의 체크포인트에서 `export_web_policy --index`로 `by_players["2".."5"]`와 6인 항목을 만든다. 체크포인트 본문은 run 아티팩트에 있고 에이전트 환경에서는 프록시 403이라, 내보내기는 CI 워크플로 안에서 해야 한다.
3. (b) 인원별 단독 c1 측정(결정 1의 표) — 다시 여는 조건에 걸릴 때만.
4. c1 9인 첫 측정(결정 2).
5. 같은 파드·같은 반복 수의 6인 단독 c1 run으로 D 배수 측정(결정 3).

## 한계
- (b)는 측정이 없어 결정 1은 측정값끼리의 비교가 아니라 구조(공유 키 0.04%)와 운영 비용에 기댄다.
- mixn 값은 시드 3개·40,000회 하나다. 수렴 정책이 아니다(필드 음수, 연구 노트 §해석).
- it/s는 파드 호스트에 따라 1.3배 이상 흔들린다. 반복 수를 고정한 비교만 했다.
