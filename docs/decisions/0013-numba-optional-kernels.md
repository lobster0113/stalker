# ADR 0013: 학습 내부 루프에 numba(선택 의존성)

- 상태: 제안 → 이 PR 머지로 채택
- 이슈: #201

## 문제
- 공식 수치가 될 TP 등급 비교에는 10⁶–10⁷ 반복이 필요하다. 지금은 1만~3만 회에서 등급 차이가 오차 안에 묶인다(#187, #188).
- E2 MCCFR의 시간 80%가 보드마다 1326 조합 강도표를 만드는 7장 평가(numpy 벡터화)였다(로컬 프로파일).
- CLAUDE.md는 "순수 Python + numpy 우선, 새 의존성은 이유와 함께"라고 정한다.

## 결정
- `numba`를 **선택 의존성**으로 둔다(`pip install -e ".[fast]"`). 첫 커널은 7장 평가기(`stalker/core/fast_eval.py`)다.
- numba가 없으면 기존 numpy 구현으로 돌아간다. **결과는 설치 여부와 무관하고 속도만 다르다.**
  - 테스트로 강제한다: 무작위 3만 핸드 + 족보별 경계 핸드 일치, 폴백 경로 일치.
  - 같은 시드의 MCCFR 정책 해시도 일치한다(로컬 확인).
- 심판(`referee/`)은 numba를 쓰지 않는다. 독립 구현 원칙에 따라 LBR·Gate는 지금 평가기를 유지한다.
- CI의 `gates`는 `[dev]`만 설치한다. 커널 함수는 numba가 없으면 순수 Python으로 돌기 때문에, 테스트가 커널 경로를 강제로 켜서(`HAVE_NUMBA = True`) numpy 경로와 결과를 비교한다. 그래서 커널 로직도 CI에서 검증된다. 학습 잡(`train.yml`, #222)은 이미 `.[fast]`를 설치한다.

## 대안
- 순수 numpy 유지: 이미 벡터화돼 있어 남은 여지가 작다.
- C 확장 직접 작성: 빌드·배포 부담이 크고, 루틴이 다루기 어렵다.
- PyPy: numpy 호환성과 CI 설정 부담이 있다.

## 후속
- 강도표 랭킹 커널(`rank_runouts`)은 이 PR에 포함한다. 같은 난수 추출에서 numpy 경로와 결과가 같다(테스트).
- 1단계(플랍 강도표 사전계산)는 보류한다. 플랍 22,100개 × 1,326 콤보 표(약 230 MB, 계산 수 시간)보다 캐시 + 컴파일 커널이 싸다. 학습 중 보드는 대부분 한 번만 나와 사전계산 이득이 작다.
- 처리량 목표(500 it/s, CI 러너)는 #201에서 달성했다(634.4 it/s, 위 표). 결과는 비트 단위로 그대로다:
  - 강도표 커널: 플러시가 불가능한 콤보의 점수는 두 랭크에만 달려 있으므로 런아웃마다 랭크 쌍(≤91)만 평가하고 플러시 가능 콤보는 개별 평가한다. 순위는 (값, 개수) 항목으로 세어 numpy 경로와 같은 정수(이긴 수, 비긴 수)와 같은 식을 쓴다.
  - 걷기: 쇼다운 승패와 플레이어·스트리트별 버킷은 딜마다 한 번, 합법 행동은 베팅 기록마다 한 번, 현재 전략은 그 키의 regret이 바뀔 때까지 캐시한다. `rng.choice` 대신 같은 난수 한 개와 같은 규칙의 `_sample`.
  - 테스트(`tests/test_e2_throughput_equivalence.py`): #201 이전 걷기(참조 구현)와 regret·정책·RNG 상태가 같다, `_sample` = `rng.choice`, 커널(numba 없이도 순수 Python으로) = numpy 강도표(플러시 많은 보드 포함).
- 플랍 강도표 사전계산(#201 1단계)은 하지 않았다. 남은 시간(로컬 프로파일)은 Python 걷기(노드당 약 12 µs: `step`, 키 문자열, 작은 numpy 배열 연산)가 약 70%, 강도표가 약 25%(그중 `rng.choice` 런아웃 추출 약 40 µs/표 — 바꾸면 표가 달라진다)다. 더 필요하면 다음은 트리 걷기 커널(정보 집합 정수 키·regret 배열)이다.
