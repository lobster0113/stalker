# STALKER 개발 계획서 — 포커 시뮬레이터와 학습 서비스 (v1.1)

- 작성: 2026-10-27, 대화 세션. **v1.1(같은 날)**: 사용자가 준 설계 리뷰(`docs/research/2026-10-27-design-review.md`)를 ADR 0010으로 반영했다. 바뀐 점은 §9 변경 기록.
- 근거: `docs/ORIGIN.md`(사용자 원문), `docs/CHARTER.md`, `docs/TP.md` v0.1, `referee/GATES.md`, ADR 0005·0008·0009·0010
- 성격: **계획**이다. 확정 사항은 ADR과 이슈 수용 기준이 정한다. 일정은 날짜가 아니라 **증거 기반 Go/No-Go**로 진행한다(§5).
- 수치 표기: "실측(로컬)"은 개발 PC에서 잰 참고값, "추정"·"초기안"은 검증 전 가정이다. 판정 근거는 CI뿐이다(헌장 1원칙). 비용·처리량 추정은 **승인 근거로 쓰지 않는다**(처리량 파일럿 전).

## 0. 한 장 요약

| 항목 | 계획 |
|---|---|
| 만들 것 | ① 정확하고 빠른 포커 시뮬레이터(캐시·토너먼트) ② TP를 거쳐서만 행동하는 정책(TP-GTO)과 페르소나 AI ③ 학습 서비스(Training Game·학습 섹션·복기) |
| 개발 트랙 | **서비스 트랙**: D1 데모(진행 중) → 서비스 골격. **연구 트랙**: Stage 0 정답 계약 → Stage 1 작은 시험대(장난감 게임·E1) → Stage 2 현실 스팟 1개 → Stage 3 토너먼트 확장. 두 트랙은 독립이고, 연구 결과가 승인 상태에 도달한 만큼만 서비스 정답이 된다 |
| 가장 먼저 할 것 | TP의 **의미**(정의식·가정·N/A)와 **정보 계약**(공개 관측 / 교사 / 엔진 상태)을 고정. 그 전에는 대규모 학습을 하지 않는다 |
| 시뮬레이터 핵심 결정 | 이미 있는 엔진(PokerKit 래퍼 `Hand` + `FastHand`, 9인 약 4,400핸드/초/코어 실측(로컬), 규칙 실행만)을 **캐시게임 모드로 확장**한다. Rust 전환은 프로파일에서 엔진이 30%를 넘을 때만 |
| 정확성 전략 | 세 구현(PokerKit, FastHand, 심판 독립 모델) 대조 + 경계 항목별 골든 케이스 + 엣지 케이스 생성기 + 속성 테스트 + 공개 핸드 기록 재생 + 평가기 전수 검사. Gate R 100%는 "지정 검사 집합에서 일치"이지 전체 무오류 보증이 아니다 |
| 진짜 병목 | 엔진이 아니라 교사 정답 계산(조건부 레인지·에퀴티)과 정책 추론. 비용은 **처리량 파일럿**(10³→10⁵→10⁶ 결정)으로 실측한 뒤에만 말한다 |
| 강도 판정 언어 | Q1 상대군 대비 성적 / Q2 앵커·솔버 의사결정 손실 / Q3 **발견된** 착취 이득(하한) / Q4 균형 인증(정확한 최선 응답이 가능한 환경만). "GTO 인증"은 Q4가 있는 환경에서만 |
| 학습 완료 판정 | 모델 승인 상태 `DRAFT → SIM_VALIDATED → BENCHMARKED → PEDAGOGY_APPROVED`(§3.7). 상태에 따라 화면 문구와 채점 허용 여부가 다르다 |
| 첫 연구 환경 | E0 장난감 게임(Kuhn·Leduc) → **E1 헤즈업 숏스택 푸시/폴드**. D3 성공 = E1에서 판정 체계가 작동하고 재현됨 |
| 서비스 기술 | 데모: 단일 HTML(Artifact). 완성 서비스: TypeScript + Vite + Preact, 정적 자산 분리, IndexedDB, JSON 내보내기/가져오기. 모델 추론은 ONNX Runtime Web(배포 스파이크로 크기·콜드 스타트 실측 후 확정) |
| 비용 | 파일럿 전까지 유료 연산 0. 사용자 결정 월 상한 $100(RunPod 선불 $100 충전됨, NH-1). 파일럿 결과로 다시 보고 |
| 사용자 결정 | 데모·서비스 체험 피드백(NH-3). 상한을 넘어야 하면 근거와 함께 다시 묻는다 |

## 1. 전체 구조

```
┌──────────────────────────── 오프라인 (Python, CI·클라우드) ────────────────────────────┐
│                                                                                         │
│  [시뮬레이터]                       [AI]                              [데이터 빌드]      │
│  stalker/tournament ──────────▶  stalker/tp     (TP 명세·교사·채점)    stalker/service   │
│   ├ rules: Hand / FastHand        stalker/personas (난이도 1~19)        ├ 문제 은행 JSON  │
│   ├ modes: Tournament / Cash      stalker/tpgto  (모델·학습·내보내기)   ├ 페르소나 파라미터│
│   ├ env:   관측·기억·오라클 훅      └ export → tpgto_<env>_<tier>.onnx   └ 모델(.onnx)    │
│   └ batch: 병렬 러너·기록                                                               │
│                                                                                         │
│  [심판 referee/]  Gate R(규칙) · L(정보 경계) · T(TP 경유) · S(둔감성) · Q(강도) · F(따라 하기) · U(웹) · E(학습 효과) │
└─────────────────────────────────────────────────────────────────────────────────────────┘
                                          │ 빌드 시 정적으로 묶음
                                          ▼
┌──────────────────────────── 온라인 (브라우저, 단일 HTML) ───────────────────────────────┐
│  web/  ├ 게임 루프(JS 규칙 엔진 = Python 엔진의 이식, 같은 테스트 벡터로 검증)           │
│        ├ TP-GTO 추론(ONNX Runtime Web, WASM)  ├ 페르소나 봇(파라미터 기반)                │
│        ├ 채점기(TP 명세 그대로)               ├ 약점 기록·추천(로컬 + Artifact 저장)      │
│        └ 화면: 시작 · Training Game · 학습 섹션 · 복기 · 내 약점                         │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

원칙
1. **규칙은 한 곳에서 정의하고 여러 곳에서 검증한다.** 규칙 명세는 `referee/GATES.md` Gate R이다. Python 엔진 두 개와 브라우저 엔진 하나가 모두 같은 테스트 벡터를 통과해야 한다.
2. **TP 명세가 계약이다.** AI 출력·채점·UI 입력 위젯이 모두 `stalker/tp/spec/tp_v<N>.json`에서 생성되거나 그것과 일치 검사를 받는다.
3. **무거운 계산은 오프라인에서, 서비스는 가볍게.** 단, Training Game은 매번 새 상황이 나오므로 TP-GTO 추론만은 브라우저에서 한다.

## 2. 포커 시뮬레이터

### 2.1 요구사항

| ID | 요구 | 근거 | 검증 |
|---|---|---|---|
| SIM-1 | 규칙이 정확하다(NLHE, 캐시·토너먼트) | 원문 "잘못 개발하면 이후 학습이 무의미" | Gate R 100% |
| SIM-2 | 같은 시드·같은 액션이면 같은 결과 | 재현성(CLAUDE.md) | 기록 해시 비교 테스트 |
| SIM-3 | 학습에 충분히 빠르다 | D3 학습 규모 | 처리량 벤치 + 프로파일 |
| SIM-4 | 정책은 공개 정보만 본다 | 헌장 5 | Gate L |
| SIM-5 | 환경이 식별된다(`env_id`) | 헌장 4 환경 분리 | 기록 스키마 검사 |
| SIM-6 | 결정마다 TP 정답을 계산할 수 있다(특권 정보 사용, 정책 입력과 분리) | ADR 0009 항목 의미 고정 | Gate T2, 오라클 단위 테스트 |
| SIM-7 | 브라우저 엔진과 결과가 같다 | 서비스 정확성 | 공유 테스트 벡터 |

결론: 시뮬레이터는 **새로 만들지 않고 확장한다.** 빠진 것은 캐시게임 모드, 환경 식별, TP 오라클 훅, 배치 러너, 브라우저 이식이다.

### 2.3 계층 설계

```
L1 rules     HandState 인터페이스: deal / legal() / apply(action) / settle() → HandResult
             구현: Hand(PokerKit, 정답) · FastHand(학습용) · web 엔진(서비스용)
L2 modes     TournamentDirector(기존 director)  ·  CashSession(신규)
             공통: 좌석·버튼·블라인드 스케줄·이벤트 스트림(Event)·game_id
L3 env       MultiAgentEnv: reset(env_spec, rng) / step(seat, action)
             정보 계약 3층 (docs/TP.md §2):
               PublicObservation  → 정책 입력 (ObservationBuilder + DecisionContext)
               TeacherContext     → 오프라인 정답 레이블 (가정한 상대 정책·설정). 숨은 카드 없음
               PrivateWorldState  → 엔진 전용 (실제 홀카드·덱). 정산·정합성 검사만
             정책 경로의 TeacherContext·PrivateWorldState 사용은 Gate L7(숨은 카드 교체 불변)·L8(런타임 출처 표지)로 막는다
L4 batch     ProcessPool 러너: 작업 = (env_spec, 정책 묶음, 시드 범위, 게임 수) → 기록 샤드
             시드 = SeedSequence(root, env_id, shard) → 재현 가능, 샤드 독립
L5 records   schema v2: DecisionRecord에 env_id·tp_version·decision_context·tp_label(교사 값 + 가정 ID)·tp_policy(정책 값) 추가
```

모듈 배치(제안): 기존 `stalker/tournament/`를 유지하고 새 최상위 엔진 패키지는 만들지 않는다.
- `stalker/tournament/cash.py` — `CashSession`
- `stalker/env/spec.py` — `EnvSpec`, `env_id`
- `stalker/env/teacher.py` — `TeacherContext`, 교사 레이블 계산
- `stalker/batch/runner.py` — 병렬 러너

### 2.4 캐시게임 규칙 명세 (v1) — Gate R에 추가할 내용

| 항목 | v1 규칙 | 이유 |
|---|---|---|
| 블라인드 | 고정 SB/BB, 앤티 없음(옵션으로 BB앤티 허용) | 일반 캐시 형식 |
| 스트래들 | 없음 | v1 단순화 |
| 레이크 | 없음(명세에 "레이크 0"으로 명시) | 학습 목표 단순화. v2에서 팟 비율·상한 레이크 추가 검토 |
| 인원 | 2~9석 고정, 세션 중 합류·이탈 없음 | 게임 = 세션. 합류 규칙(BB 대기·데드 버튼)은 v2 |
| 버튼 | 매 핸드 다음 점유 좌석 | 이탈이 없으므로 데드 버튼 불필요 |
| 리바이·탑업 | 핸드 시작 시 스택 0이면 시작 스택으로 리바이. 옵션 `auto_topup`: 스택 < 시작 스택이면 시작 스택까지 채움(기본 꺼짐) | 깊이 고정 환경(100BB) 학습용 옵션 |
| 세션 길이 | M 핸드(설정), 또는 사람 대상 서비스에서는 무제한 | 원문 "N 라운드·M 핸드" |
| 결과 | 좌석별 순손익(칩), bb/100 | Gate Q 단위 |
| 보상(학습) | 핸드별 칩 증감/BB (토너먼트는 게임 끝 상금) | 캐시는 핸드 단위 보상이 자연스럽다 |

Gate R에 추가할 검사: `cash_rebuy`(리바이 금액·시점), `cash_topup`, `button`(고정 인원), `chip_conservation`, `session_length`.

불변식(레이크 0):
- 테이블 전체: 총 종료 스택 = 총 시작 스택 + 총 리바이 + 총 탑업 − 총 인출(v1은 인출 없음)
- 좌석별 순손익 = 종료 스택 + 인출 − 시작 스택 − 리바이 − 탑업. bb/100은 이 순손익으로 계산한다(최종 스택이 아니다).

### 2.5 토너먼트 쪽 보완

| 항목 | 현재 | 계획 |
|---|---|---|
| 레벨 길이 | 핸드 수 단위만 | `length_unit=minutes` 구현: 핸드당 가상 시간(설정, 기본 테이블 인원 × 7초)으로 환산 |
| 숏스택 징수 `skip` | 미구현(`ConfigError`) | 구현 + Gate R 검사 |
| 머니인 기준·페이아웃 | 프리셋 6종 | "상위 X%" 생성기, 버블 단계 표시 |
| 단계(stage) | 없음 | 관측 요약에 `stage`(초반·중반·버블 근처·머니인·파이널 테이블) 추가 — TP §4 버킷 |
| 중간 단계에서 시작 | 없음 | `start_state` 생성기: 남은 인원·스택 분포·레벨을 지정해 게임을 중간부터 시작(버블 연습용) |

### 2.6 환경 식별 (`env_id`)

환경 = 학습을 따로 할 단위(헌장 4). `EnvSpec`의 해시로 `env_id`를 만든다.

| 축 | 캐시 | 토너먼트 |
|---|---|---|
| 종류 | `cash` | `mtt` / `sng` |
| 인원 | 2 / 6 / 9 | 테이블 6 / 9 |
| 깊이 | 시작 스택 버킷 40 / 100 / 200BB | 블라인드 구조 클래스(터보·일반·딥) |
| 지급 | — | 페이아웃 클래스(톱헤비·플랫·승자독식) × 머니인 비율 |
| 앤티 | 없음 / BB앤티 | 없음 / 일반 / BB앤티 |

- `EnvSpec`에 함께 기록할 필드: `rules_version`, `table_size`, `field_size`, `initial_stacks`, `blind_schedule`, `ante_schedule`, `payout_vector`, `payout_mode`, `reentry_rule`, `rake`(캐시, v1 = 0), `time_model`, `rng_schema_version`. `env_id` 해시에서 원래 명세 JSON을 역추적할 수 있게 저장한다.
- `env_id`는 정확한 식별자다. **학습을 환경마다 분리할지**는 별개 결정이다: 공통 인코더 + 환경 어댑터 vs 완전 분리를 D2 ADR에서 비교한다(조합 폭발 방지). 환경별 게이트 판정은 어느 쪽이든 따로 한다.
- 서비스 설정 화면의 선택지는 승인 상태가 있는 환경만 활성화한다(나머지는 "준비 중").
- 같은 환경 안의 연속 조건(실제 스택, 레벨)은 TP §4 버킷으로 다룬다(둔감성).

### 2.7 정확성 검증 계획 (가장 중요)

다섯 겹으로 막는다. 어느 하나라도 실패하면 머지하지 않는다.

1. **3자 일치(Gate R 확장).** PokerKit `Hand`, `FastHand`, 심판 독립 모델이 같은 이벤트 스트림에서 칩 단위로 같은 결과를 내야 한다. 캐시 모드가 생기면 같은 스위트에 캐시 프리셋을 추가한다.
2. **엣지 케이스 생성기.** 무작위 플레이로는 드문 상황을 일부러 만든다. 시드를 고정해 매 CI에서 같은 세트를 돈다.
   - 숏 올인 연쇄(풀 레이즈 미만 올인 2~3회 뒤 재오픈 여부)
   - 3개 이상 사이드팟 + 동점 분할 + 홀수 칩
   - 앤티로만 올인한 좌석의 팟 자격
   - 블라인드를 다 못 내는 좌석(SB·BB 숏)
   - 헤즈업 전환 직후 버튼·블라인드 위치
   - 같은 핸드 다중 탈락의 순위(시작 스택 순, 동률 추첨)
   - 보드로 플레이(5장 보드가 최고 핸드) 분할
   - 휠·스티블 스트레이트, 플러시 대 플러시 키커
3. **속성 테스트(hypothesis 추가 제안).** 임의 액션 열에서: 칩 보존, 합법 액션만 적용됨, 최소 레이즈 규칙, 팟 합 = 기여 합, 결과가 좌석 순서 회전에 불변(같은 카드·같은 상대 위치 기준).
4. **공개 핸드 기록 재생(골든 핸드).** PHH 형식 공개 데이터셋(PokerKit 저자의 PHH 데이터셋: 공개 대회·AI 대국 핸드)을 내려받아 고정 커밋으로 저장하고, 기록된 최종 스택과 엔진 결과가 같은지 확인한다. 라이선스를 확인하고 PR 본문에 적는다. 목표 1만 핸드 이상.
5. **평가기 전수 검사.** 5장 조합 2,598,960개를 전부 평가해 등급 7,462개 분포(스트레이트 플러시 40, 포카드 624, …)와 일치, 7장 평가기는 무작위 10⁶개를 "21개 5장 조합 중 최대"와 대조.

리뷰 규칙(하네스에 반영됨): 엔진 규칙을 바꾸는 PR은 그 규칙을 다루는 Gate R 검사를 같은 PR에 추가해야 한다. Reviewer가 규칙 명세와 대조한다(`harness/routines/reviewer.md` 10항).

브라우저 엔진 검증: Python 엔진으로 만든 **테스트 벡터 파일**(시드·액션 열 → 핸드별 결과, 1만 핸드)을 `web/tests/vectors/`에 두고, JS 엔진이 Node에서 같은 결과를 내는지 CI에서 확인한다.

### 2.8 성능 계획

| 단계 | 목표 | 방법 | 판단 |
|---|---|---|---|
| 엔진 단독 | ≥ 4,000핸드/초/코어(9인) | `FastHand` 현재 수준 유지, 회귀 감시 벤치를 CI slow 잡에 | 회귀 20% 이상이면 경보 |

### 2.9 교사 정답 (TeacherContext)

### 3.2 모델 구조 (ADR 0009 추천안 구체화)

```
관측(공개) ──▶ 인코더 (좌석 토큰 트랜스포머 2층 × d=128 + 카드 임베딩 + 이력 GRU)

```

- 파라미터 규모 목표: 1~3M(브라우저 추론, ONNX int8 양자화 후 5MB 이하).
- 등급: 먼저 **한 정책 + 등급별 TP 양자화**(액션 헤드 입력을 등급 눈금으로 양자화했을 때의 손실)를 잰다. 등급별 별도 학습은 EV와 교육 효과에서 확실히 나을 때만 한다.
- 멀티웨이 TP 요약(상대별 동적 리스트 vs 대표 1~2명)은 Stage 3 실험이다. v1 이론 검증은 헤즈업.
- 알고리즘: PPO는 기본 가설일 뿐이다. 장난감 게임과 E1에서 CFR 계열·PSRO와 대조 실험해 선택 근거를 남긴다.

### 3.5 페르소나 AI (난이도 1~19)

파라미터 기반 규칙 봇으로 시작하고(D2), 나중에 TP-GTO 정책에 성향 편향을 주입한 버전으로 바꾼다(D3 이후).

페르소나는 **실력 등급 × 스타일 × 적응력 × 무작위성**의 네 축으로 정의한다(ADR 0010). 스타일(스테이션·매니악·나이트·TAG·LAG)은 실력 순서가 아니다. 난이도는 같은 실력 등급 안에서 스타일을 섞어 구성하고, 난이도 순위는 여러 기준 정책과 좌석 교환으로 잰 성적으로 검증한다. 난이도 20은 "가장 강한 승인 모델"이며 화면 문구는 그 모델의 승인 상태를 따른다. 아래 표는 초기 스타일 파라미터 예시다.

| 난이도 | 구성(테이블 좌석 비율) | 대표 유형 파라미터(VPIP/PFR/공격성/폴드 성향) |
|---|---|---|
| 1~4 | 콜링 스테이션·루즈 패시브·매니악·위크 타이트 | 55/5/.12/.12, 42/9/.25/.35, 62/42/.85/.25, 17/8/.22/.78 |
| 5~9 | 나이트·위크 타이트·TAG·루즈 패시브·스테이션 | 12/10/.40/.68 외 |
| 10~14 | TAG·LAG 중심 + 약한 유형 1~2명 | 22/18/.56/.50, 30/25/.66/.40 |
| 15~19 | 하이스테이크 프로·LAG·TAG | 24/20/.60/.45 |
| 20 | TP-GTO(최고 등급 모델) | — |

검증: 페르소나 충실도(10만 핸드에서 실측 VPIP·PFR·공격성이 목표 ±3%p), 난이도 단조성(난이도 n+1 필드가 n 필드보다 TP-GTO에게 덜 지는가, 95% CI).

### 3.7 "학습이 충분히 되었다"의 판정 — 모델 승인 상태

정의는 `referee/GATES.md` "모델 승인 상태"와 Gate Q1~Q4가 공식이다. 여기서는 판정 절차를 정리한다. 수치는 초기안이며 판별력 측정 뒤 확정한다.

| 상태 | 필요한 증거 | 서비스 화면 |
|---|---|---|
| `DRAFT` | 형식·API | "모의" |
| `SIM_VALIDATED` | Gate R·L(L7·L8 포함)·T(T4 포함) 통과, 교사 레이블 정합성 | "검증 중", 점수 없음 |
| `BENCHMARKED` | A 수렴 + Gate S·Q·F 결과 기록 + 시드 간 동등성 | "검증 중", 강도 수치·적용 환경 표시 |
| `PEDAGOGY_APPROVED` | 정답 안정 + 항목별 채점 승인 + (D4) Gate X | "검증 완료", 채점·추천 허용 |

#### A. 수렴 (학습 내부 신호)
- 정책 변화량: 고정 평가 스팟 세트(개발 세트)에서 연속 체크포인트 간 액션 분포 KL 평균 < 0.005, 판단 항목 변화 95백분위 < 2. 연속 3회.
- 과거 자신과의 대국: 현재 대 5개 전 체크포인트의 차이가 동등성 범위(±δ_eq) 안 — 연속 2회.
- 붕괴 감시: 베팅을 마주한 결정의 폴드 비율 > 0.95 또는 레이즈 비율 < 0.02이면 수렴으로 보지 않는다(구 RL의 체크/폴드 붕괴, #78).
- 수렴은 필요조건일 뿐이다. 나쁜 국소해일 수 있다.

#### B. 강도 (Gate Q1~Q4 — 무엇을 주장할 수 있는가)
| 환경 | 측정 | 쓸 수 있는 문구 |
|---|---|---|
| E0·E1 | 정확한 최선 응답(Q4) | "이 환경에서 착취 가능성 ≤ X"(초기안: E1 고수 등급 ≤ 0.03bb/핸드, 초보 ≤ 0.10) |
| E2 이후 | 앵커·솔버 스팟 손실(Q2), LBR·학습된 공격자(Q3), 페르소나 필드(Q1) | "이 상대군 대비 +Y", "솔버 스팟 대비 손실 Z", "**발견된** 착취 이득 W(하한)". 상한·인증 문구는 쓰지 않는다 |

- 복잡성 비용: 같은 환경의 병목 없는 기준 정책 대비 차이를 등급별로 보고한다.
- 공격자는 심판 소유(`referee/exploit/`), TP-GTO 학습에 쓰지 않은 시드·코드 경로.

#### C. 게이트
Gate T(T1~T4) 100%, L 100%, S(regret 기반 + 민감 골든 스팟), Q1(최상위 페르소나 필드 대비 95% CI 하한 > 0), F(합성 오차 모델로 판정, 시간 압박·실측은 별도 보고), 적응 가치(기억 끈 모델 대비 EV 이득).

#### D. 재현
- 학습 시드 3개. 판정은 CI 겹침이 아니라 **동등성 검정**(차이의 90% CI가 [−δ_eq, δ_eq] 안). 평균·분산·최악 시드를 사전 등록한 규칙으로 보고하고, 실패 시 재학습 정책도 사전 등록한다.
- 체크포인트 선택은 순환 검증 세트로, 최종 보고는 최종 블라인드 감사 세트(`HOLDOUT_SEED`)로 한다. 다중 비교는 Holm 보정.

#### E. 정답 안정 (가르쳐도 되는가)
- 세 시드 모델 간 판단 항목 차이 95백분위 ≤ 등급 눈금 한 칸, 주 액션 일치율 ≥ 85%. 못 넘는 항목은 `eligible_for_grading=false`(참고값으로만 표시).

#### 판정 결과와 그 다음
| 결과 | 다음 행동 |
|---|---|
| `PEDAGOGY_APPROVED` | 모델 카드(환경·승인 상태·Q1~Q4 결과·복잡성 비용) 작성, `referee/champions/<env_id>/`에 등록, 서비스 정답 교체 |
| 수렴했지만 Q·S 실패 | 상대 풀·탐색·알고리즘 대조 실험. 그래도 실패하면 TP 재검토(ADR). 정상적인 연구 결과다 |
| Q 통과, 정답 안정 실패 | 둔감성 정규화 강화, 흔들리는 항목은 채점 제외 |
| 판정 불가(표본 부족) | 예산 안에서 표본 확대 또는 δ 재검토(ADR) |

- 재학습 조건: TP 버전 변경, 환경 축 추가, 엔진 규칙 변경, 새 공격자가 기존 모델에서 큰 착취 이득을 발견. 교체 모델은 기존 모델 대비 비열등이어야 한다.

### 4.4 화면 상세

**Training Game**
- 레이아웃: 노트북 1440px 기준 테이블 영역 약 1fr + TP 패널 392px. 태블릿 가로도 같은 배치(패널 340px). 폰 세로는 테이블 3:4 + 바텀 시트(접힘 78px, 펼침 최대 72vh, 내 차례에 자동 펼침).

- 상태: 대기(행동 중 표시·직전 채점 결과·핸드 기록) → 내 차례(TP 질문 목록 + 액션) → 제출(채점 결과, 액션 즉시 반영, 게임 계속).
- TP 패널 내용: 상황 칩(스트리트·포지션·유효 스택·팟·콜 금액·SPR), 판단 대상 상대(관측 핸드 수), 단계 묶음 B→C→D→E→F, 등급별 항목(`docs/TP.md` §3).
- "정보 부족": 대상 상대 관측 핸드 < n(명세 상수)이면 성향 항목은 입력·채점하지 않는다.
- 게임 끝: 토너먼트는 탈락·우승, 캐시는 M 핸드. 게임 요약(TP 항목별 점수, 가장 큰 손실 결정 3개, 학습 추천).

**채점 (`tp/grade.ts`)** — `docs/TP.md` §5가 공식

| 항목 종류 | 점수 |
|---|---|
| 판단·계산 항목 | 오차 ≤ 허용(등급 눈금 반 칸)이면 100, 아니면 오차에 비례 감점. N/A·채점 제외 항목은 넣지 않는다 |
| 레인지 | 초보·중수: 상위 X% 근사 오차. 고수: 콤보 가중 유사도. 레인지 오차가 후속 결정 EV에 주는 영향은 별도 표시 |
| 계산 항목 | 두 점수: ① 사용자 앞 단계 입력으로 다시 계산한 값과 비교 ② 정답과 비교 |
| 액션 | Q(s,a)가 있으면 EV 손실. 최선 대비 EV 차이 ≤ 팟의 1%(초기안)인 액션은 모두 만점. Q가 없으면 "EV 손실 미산출". 단일 핸드 빈도 감점 없음(빈도는 누적 분포로) |
| 신뢰도 라벨 | 모든 정답 화면에 `모의`/`검증 중`/`검증 완료` |

**상호작용 모드**: Quick(게임 중, 핵심 판단 1~3개 + 액션) · Guided(등급의 판단 전부) · Deep Review(복기, 169칸·가정 바꿔 보기). 결정당 입력 시간 P50/P95와 10핸드 후 이탈률을 기록한다. 액션 먼저 → 나중에 분석 요청 흐름도 지원.

**학습 섹션**
- 문제 생성기: 항목 × 난이도마다 함수 하나(`generators/<item>.ts`). 정답은 D1~D2는 JS 몬테카를로, D3부터 사전계산 문제 은행(오라클 값) + 모델.
- 출제: 약점 가중(최근 20문제 평균이 낮은 항목 3배 가중) + 간격 반복(틀린 유형은 1·3·7일 뒤 다시).
- 피드백: 정답·내 답 막대 비교, 한 줄 설명(규칙 기반 문장), "왜"를 보는 펼침(레인지 그림·에퀴티 분포).

**복기**
- 입력: 카드 피커(52장 그리드), 포지션·스택, 스트리트별 액션 타임라인(좌석·액션·사이즈를 칩으로 추가), 또는 핸드 기록 텍스트 붙여넣기(D4: 주요 사이트 형식 파서, 개인 기록 전용).
- 분석: 결정 지점마다 상대 가정별(타이트/보통/루즈) **조건부 조언**, 모든 가정에서 공통으로 안전한 판단, 결론이 뒤집히는 임계점, "가장 크게 갈린 판단". 상대 정책을 모르므로 "유일한 정답"으로 표시하지 않는다.
- 비슷한 상황 생성: 같은 핸드 클래스·같은 보드 텍스처 군(페어드·모노톤·연결성)·같은 스택 버킷으로 시드를 만들어 Training Game 시작(데모는 무늬만 바꾸는 방식).

## 5. 진행 방식 — 날짜가 아니라 증거 기반 Go/No-Go

두 트랙을 독립적으로 진행한다. 아래 순서는 우선순위이고, 각 단계의 Go/No-Go를 통과해야 다음 단계 이슈를 연다(Planner 책임).

### 서비스 트랙
| 단계 | 내용 | Go/No-Go |
|---|---|---|
| D1 | Gate U, TP 명세 v0.1 JSON, 데모 정정(라벨·채점 문구·입력 시간), Quick/Guided, 내보내기 | 3종 화면 전 흐름, 결정당 입력 시간 기록, 사용자 피드백 반영. 반복해서 할 만큼 짧고 이해되는가 — 아니면 TP 항목 추가 중단 |
| D2 | `web/app` 골격, 배포 스파이크, 테이블·TP 패널 이식, 웹 엔진, 학습 섹션·복기 | 배포 방식 ADR, 웹 엔진 벡터 일치 |
| D3 이후 | 승인된 모델 연결, 문제 은행 | 승인 상태에 따라 라벨 |

### 연구 트랙
| 단계 | 내용 | Go/No-Go |
|---|---|---|
| Stage 0 정답 계약 | TP v0.1 의미 정의(손계산 사례 포함), 정보 계약 3층, DecisionContext, 첫 환경 1개(E1)·첫 정답 항목 3~5개 확정 | 레인지·에퀴티·콜 가격·액션 채점의 손계산 사례가 코드와 일치 — 아니면 학습 착수 보류 |
| Stage 1 작은 시험대 | E0 장난감 게임, E1 푸시/폴드: 병목 정책·무제약 정책·정확한 기준 비교, 복잡성 비용–입력 시간 곡선 | TP 제한에 강도·설명성 이점이 전혀 없으면 TP 재설계 |
| Stage 1.5 시뮬레이터 확장 | 캐시 모드·Gate R 확장·골든 케이스·처리량 파일럿 | 파일럿 로그로 비용 보고(필요하면 예산 재요청) |
| Stage 2 현실 스팟 1개 | E2(D2 ADR로 선택), 문제 은행 우선, 한 정책 + 양자화 비교, 알고리즘 대조 | 승인 상태 `BENCHMARKED` |
| Stage 3 확장 | 멀티웨이 TP 요약, 9인 SNG ICM, MTT 공개 요약·전역 시계 | 환경별 승인 상태 |

- **D3 성공 = E1에서 승인 판정 체계가 실제로 작동하고 재현됨.** E1 모델이 기준을 못 넘는 것은 실패가 아니라 연구 결과다(진행 상태: `engine-ready` → `trainable` → `benchmark-pass` → `pedagogy-ready`).
- 첫 주 우선순위(하네스): 하네스 #102~#105, D1 #99·#100, 연구 Stage 0 계약 이슈들, 선행 없는 SIM-a·SIM-d·SIM-e·SIM-g.

## 9. 변경 기록

### v1.1 (2026-10-27) — 설계 리뷰 반영 (ADR 0010)
- 정보 계약 3층(`PublicObservation`/`TeacherContext`/`PrivateWorldState`), `OracleView` → `TeacherContext`. 숨은 카드는 정답 계산에도 쓰지 않는다(§2.3, §2.9).

- TP v0.1: 항목별 정의식·N/A·채점 여부, `hand.future` → `hand.outs`·`hand.vuln`, `plan.pot` 채점 제외, `opp.bluff` → `opp.value`(가정 명시), Quick/Guided/Deep 모드.
- 강도 판정 Q1~Q4, "GTO 인증"은 Q4 환경만. 학습 완료 판정을 모델 승인 상태로(§3.7).
- 액션 채점: 확률비 폐기, Q(s,a) 기반 EV 손실·EV 동률 허용·Q 없으면 미산출(§4.4).
- Gate S regret 기반 + 민감 골든 스팟. 통계: 동등성 검정, 세트 3분할, Holm, 꼬리.
- 일정 → 증거 기반 Go/No-Go, D3 성공 = E1 판정 체계 작동·재현. E0 장난감 게임 추가(§3.4, §5).
- 비용: 처리량 파일럿 전에는 추정치를 승인 근거로 쓰지 않음(§2.8, §6).
- 캐시 탑업 불변식, `EnvSpec` 필드 확장, SIM-c0을 SIM-b 앞으로(DOC-07·11·14), 구조도 패키지명(DOC-06).
- 서비스: 데모 단일 HTML vs 완성 서비스 정적 자산·IndexedDB·내보내기, 배포 스파이크, 복기 조건부 조언(§4).
