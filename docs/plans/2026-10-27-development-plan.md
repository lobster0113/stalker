# STALKER 개발 계획서 — 포커 시뮬레이터와 학습 서비스

- 작성: 2026-10-27, 대화 세션(방향 전환 직후, ADR 0008)
- 근거: `docs/ORIGIN.md`(사용자 원문), `docs/CHARTER.md`, `docs/TP.md` v0, `referee/GATES.md`, ADR 0005·0008·0009
- 성격: **계획**이다. 확정 사항은 ADR과 이슈 수용 기준이 정한다. 일정은 하네스 처리량(최근 3일 머지 43건, 하루 약 14건) 기준 추정이다.
- 수치 표기: "실측(로컬)"은 개발 PC에서 잰 참고값, "추정"은 계산·문헌 기반 가정이다. 판정 근거는 CI뿐이다(헌장 1원칙).

## 1. 전체 구조

```
┌──────────────────────────── 오프라인 (Python, CI·클라우드) ────────────────────────────┐
│                                                                                         │
│  [시뮬레이터]                       [AI]                              [데이터 빌드]      │
│  stalker/engine  ─────────────▶  stalker/tp     (TP 명세·오라클·채점)  stalker/service   │
│   ├ rules: Hand / FastHand        stalker/personas (난이도 1~19)        ├ 문제 은행 JSON  │
│   ├ modes: Tournament / Cash      stalker/tpgto  (모델·학습·내보내기)   ├ 페르소나 파라미터│
│   ├ env:   관측·기억·오라클 훅      └ export → tpgto_<env>_<tier>.onnx   └ 모델(.onnx)    │
│   └ batch: 병렬 러너·기록                                                               │
│                                                                                         │
│  [심판 referee/]  Gate R(규칙) · L(정보 경계) · T(TP 경유) · S(둔감성) · Q(강도) · F(따라 하기) · U(웹) · E(학습 효과) │
└─────────────────────────────────────────────────────────────────────────────────────────┘
                                          │ 빌드 시 정적으로 묶음
                                          ▼
┌──────────────────────────── 온라인 (브라우저, 단일 HTML) ───────────────────────────────┐
│  web/  ├ 게임 루프(JS 규칙 엔진 = Python 엔진의 이식, 같은 테스트 벡터로 검증)           │
│        ├ TP-GTO 추론(ONNX Runtime Web, WASM)  ├ 페르소나 봇(파라미터 기반)                │
│        ├ 채점기(TP 명세 그대로)               ├ 약점 기록·추천(로컬 + Artifact 저장)      │
│        └ 화면: 시작 · Training Game · 학습 섹션 · 복기 · 내 약점                         │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

원칙
1. **규칙은 한 곳에서 정의하고 여러 곳에서 검증한다.** 규칙 명세는 `referee/GATES.md` Gate R이다. Python 엔진 두 개와 브라우저 엔진 하나가 모두 같은 테스트 벡터를 통과해야 한다.
2. **TP 명세가 계약이다.** AI 출력·채점·UI 입력 위젯이 모두 `stalker/tp/spec/tp_v<N>.json`에서 생성되거나 그것과 일치 검사를 받는다.
3. **무거운 계산은 오프라인에서, 서비스는 가볍게.** 단, Training Game은 매번 새 상황이 나오므로 TP-GTO 추론만은 브라우저에서 한다.

## 2. 포커 시뮬레이터

### 2.1 요구사항

| ID | 요구 | 근거 | 검증 |
|---|---|---|---|
| SIM-1 | 규칙이 정확하다(NLHE, 캐시·토너먼트) | 원문 "잘못 개발하면 이후 학습이 무의미" | Gate R 100% |
| SIM-2 | 같은 시드·같은 액션이면 같은 결과 | 재현성(CLAUDE.md) | 기록 해시 비교 테스트 |
| SIM-3 | 학습에 충분히 빠르다 | D3 학습 규모 | 처리량 벤치 + 프로파일 |
| SIM-4 | 정책은 공개 정보만 본다 | 헌장 5 | Gate L |
| SIM-5 | 환경이 식별된다(`env_id`) | 헌장 4 환경 분리 | 기록 스키마 검사 |
| SIM-6 | 결정마다 TP 정답을 계산할 수 있다(특권 정보 사용, 정책 입력과 분리) | ADR 0009 항목 의미 고정 | Gate T2, 오라클 단위 테스트 |
| SIM-7 | 브라우저 엔진과 결과가 같다 | 서비스 정확성 | 공유 테스트 벡터 |

| `stalker/tournament/fast_hand.py` `FastHand` | PokerKit 규칙·덱 소비 순서 복제, 같은 인터페이스 | 9인 약 4,400핸드/초/코어 실측(로컬, PokerKit 대비 약 55배) |

결론: 시뮬레이터는 **새로 만들지 않고 확장한다.** 빠진 것은 캐시게임 모드, 환경 식별, TP 오라클 훅, 배치 러너, 브라우저 이식이다.

### 2.3 계층 설계

```
L1 rules     HandState 인터페이스: deal / legal() / apply(action) / settle() → HandResult
             구현: Hand(PokerKit, 정답) · FastHand(학습용) · web/engine.ts(서비스용)
L2 modes     TournamentDirector(기존 director)  ·  CashSession(신규)
             공통: 좌석·버튼·블라인드 스케줄·이벤트 스트림(Event)·game_id
L3 env       MultiAgentEnv: reset(env_spec, rng) / step(seat, action)
             관측: ObservationBuilder(공개 정보만) → 정책
             오라클 훅: OracleView(특권 정보: 모든 홀카드·상대 정책) → TP 정답. 정책 쪽에서 import 불가(테스트로 강제)
L4 batch     ProcessPool 러너: 작업 = (env_spec, 정책 묶음, 시드 범위, 게임 수) → 기록 샤드
             시드 = SeedSequence(root, env_id, shard) → 재현 가능, 샤드 독립
L5 records   schema v2: DecisionRecord에 env_id·tp_version·tp_truth(오라클 값)·tp_policy(정책 값) 추가
```

모듈 배치(제안): `stalker/tournament/`는 그대로 두고 `stalker/engine/`을 새로 만들지 않는다. 대신
- `stalker/tournament/cash.py` — `CashSession`
- `stalker/env/spec.py` — `EnvSpec`, `env_id`
- `stalker/env/oracle.py` — `OracleView`
- `stalker/batch/runner.py` — 병렬 러너

### 2.4 캐시게임 규칙 명세 (v1) — Gate R에 추가할 내용

| 항목 | v1 규칙 | 이유 |
|---|---|---|
| 블라인드 | 고정 SB/BB, 앤티 없음(옵션으로 BB앤티 허용) | 일반 캐시 형식 |
| 스트래들 | 없음 | v1 단순화 |
| 레이크 | 없음(명세에 "레이크 0"으로 명시) | 학습 목표 단순화. v2에서 팟 비율·상한 레이크 추가 검토 |
| 인원 | 2~9석 고정, 세션 중 합류·이탈 없음 | 게임 = 세션. 합류 규칙(BB 대기·데드 버튼)은 v2 |
| 버튼 | 매 핸드 다음 점유 좌석 | 이탈이 없으므로 데드 버튼 불필요 |
| 리바이·탑업 | 핸드 시작 시 스택 0이면 시작 스택으로 리바이. 옵션 `auto_topup`: 스택 < 시작 스택이면 시작 스택까지 채움(기본 꺼짐) | 깊이 고정 환경(100BB) 학습용 옵션 |
| 세션 길이 | M 핸드(설정), 또는 사람 대상 서비스에서는 무제한 | 원문 "N 라운드·M 핸드" |
| 결과 | 좌석별 순손익(칩), bb/100 | Gate Q 단위 |
| 보상(학습) | 핸드별 칩 증감/BB (토너먼트는 게임 끝 상금) | 캐시는 핸드 단위 보상이 자연스럽다 |

Gate R에 추가할 검사: `cash_rebuy`(리바이 금액·시점), `cash_topup`, `button`(고정 인원), `chip_conservation`(세션 전체: 칩 합 = 시작 합 + 리바이 합), `session_length`.

### 2.5 토너먼트 쪽 보완

| 항목 | 현재 | 계획 |
|---|---|---|
| 레벨 길이 | 핸드 수 단위만 | `length_unit=minutes` 구현: 핸드당 가상 시간(설정, 기본 테이블 인원 × 7초)으로 환산 |
| 숏스택 징수 `skip` | 미구현(`ConfigError`) | 구현 + Gate R 검사 |
| 머니인 기준·페이아웃 | 프리셋 6종 | "상위 X%" 생성기, 버블 단계 표시 |
| 단계(stage) | 없음 | 관측 요약에 `stage`(초반·중반·버블 근처·머니인·파이널 테이블) 추가 — TP §4 버킷 |
| 중간 단계에서 시작 | 없음 | `start_state` 생성기: 남은 인원·스택 분포·레벨을 지정해 게임을 중간부터 시작(버블 연습용) |

### 2.6 환경 식별 (`env_id`)

환경 = 학습을 따로 할 단위(헌장 4). `EnvSpec`의 해시로 `env_id`를 만든다.

| 축 | 캐시 | 토너먼트 |
|---|---|---|
| 종류 | `cash` | `mtt` / `sng` |
| 인원 | 2 / 6 / 9 | 테이블 6 / 9 |
| 깊이 | 시작 스택 버킷 40 / 100 / 200BB | 블라인드 구조 클래스(터보·일반·딥) |
| 지급 | — | 페이아웃 클래스(톱헤비·플랫·승자독식) × 머니인 비율 |
| 앤티 | 없음 / BB앤티 | 없음 / 일반 / BB앤티 |

- 학습 단위는 이 축의 조합이다. 서비스 설정 화면의 선택지도 이 표에서 생성한다(학습되지 않은 조합은 "준비 중"으로 비활성).
- 같은 환경 안의 연속 조건(실제 스택, 레벨)은 TP §4 버킷으로 다룬다(둔감성).

### 2.7 정확성 검증 계획 (가장 중요)

다섯 겹으로 막는다. 어느 하나라도 실패하면 머지하지 않는다.

1. **3자 일치(Gate R 확장).** PokerKit `Hand`, `FastHand`, 심판 독립 모델이 같은 이벤트 스트림에서 칩 단위로 같은 결과를 내야 한다. 캐시 모드가 생기면 같은 스위트에 캐시 프리셋을 추가한다.
2. **엣지 케이스 생성기.** 무작위 플레이로는 드문 상황을 일부러 만든다. 시드를 고정해 매 CI에서 같은 세트를 돈다.
   - 숏 올인 연쇄(풀 레이즈 미만 올인 2~3회 뒤 재오픈 여부)
   - 3개 이상 사이드팟 + 동점 분할 + 홀수 칩
   - 앤티로만 올인한 좌석의 팟 자격
   - 블라인드를 다 못 내는 좌석(SB·BB 숏)
   - 헤즈업 전환 직후 버튼·블라인드 위치
   - 같은 핸드 다중 탈락의 순위(시작 스택 순, 동률 추첨)
   - 보드로 플레이(5장 보드가 최고 핸드) 분할
   - 휠·스티블 스트레이트, 플러시 대 플러시 키커
3. **속성 테스트(hypothesis 추가 제안).** 임의 액션 열에서: 칩 보존, 합법 액션만 적용됨, 최소 레이즈 규칙, 팟 합 = 기여 합, 결과가 좌석 순서 회전에 불변(같은 카드·같은 상대 위치 기준).
4. **공개 핸드 기록 재생(골든 핸드).** PHH 형식 공개 데이터셋(PokerKit 저자의 PHH 데이터셋: 공개 대회·AI 대국 핸드)을 내려받아 고정 커밋으로 저장하고, 기록된 최종 스택과 엔진 결과가 같은지 확인한다. 라이선스를 확인하고 PR 본문에 적는다. 목표 1만 핸드 이상.
5. **평가기 전수 검사.** 5장 조합 2,598,960개를 전부 평가해 등급 7,462개 분포(스트레이트 플러시 40, 포카드 624, …)와 일치, 7장 평가기는 무작위 10⁶개를 "21개 5장 조합 중 최대"와 대조.

리뷰 규칙(하네스에 반영됨): 엔진 규칙을 바꾸는 PR은 그 규칙을 다루는 Gate R 검사를 같은 PR에 추가해야 한다. Reviewer가 규칙 명세와 대조한다(`harness/routines/reviewer.md` 10항).

브라우저 엔진 검증: Python 엔진으로 만든 **테스트 벡터 파일**(시드·액션 열 → 핸드별 결과, 1만 핸드)을 `web/tests/vectors/`에 두고, JS 엔진이 Node에서 같은 결과를 내는지 CI에서 확인한다.

### 2.9 TP 오라클 (시뮬레이터 안의 "정답")

학습 중에는 모든 좌석의 정책을 알기 때문에, TP의 계산 항목과 레인지를 **정확히** 계산할 수 있다. 이것이 TP 항목이 이름대로의 의미를 갖게 하는 장치다(ADR 0009).

| TP 항목 | 오라클 계산 | 비용 대책 |
|---|---|---|
| `opp.range` | 상대 홀카드 1326콤보 사후분포: 사전(카드 제거 반영) × Π 상대 정책 π(a_t \| 콤보, 이력). 정책 평가는 콤보 배치로 한 번에 | 1326개를 한 배치로 정책 추론(신경망) 또는 규칙(페르소나) 벡터화 |
| `hand.equity` | 내 핸드 대 `opp.range` 에퀴티. 리버는 정확(1326 평가), 턴은 남은 카드 44장 전수, 플랍은 샘플 | numpy 벡터 평가기(`hu_equity.py`), 보드별 캐시 |
| `board.adv` | 내 레인지 대 상대 레인지 에퀴티(넛 비율 가중) | 1326×1326 블로커 마스크 행렬 곱. 프리플랍은 169×169 표 |
| `hand.future` | 다음 카드별 에퀴티 변화 분포 | 턴 44장·리버 전수, 캐시 |
| `opp.bluff` | `opp.range` 중 내 콜링 기준보다 강한 비율 | 위 결과 재사용 |
| `plan.icm` | ICM 기준 필요 에퀴티 − 칩EV 기준 필요 에퀴티 | `core/icm.py` 정확해(생존 ≤9), 그 이상은 MC |
| `act.foldprob` | 상대 정책의 이 사이즈 폴드 확률을 `opp.range`로 가중 평균 | 정책 배치 추론 1회 |
| `opp.loose/aggr/foldy` | 이 게임 관측 통계의 베이지안 수축 추정(사전 = 모집단) | `GameMemoryStore` 통계 재사용 |

`OracleView`는 정책 쪽 코드에서 import할 수 없게 한다(Gate L에 "오라클 격리" 검사 추가).

### 3.2 모델 구조 (ADR 0009 추천안 구체화)

```
관측(공개) ──▶ 인코더 (좌석 토큰 트랜스포머 2층 × d=128 + 카드 임베딩 + 이력 GRU)
```

### 3.7 "GTO 학습이 충분히 되었다"의 판정

한 환경·한 등급의 TP-GTO 체크포인트를 **"학습 완료(서비스 정답으로 사용 가능)"**로 선언하려면 아래 다섯 조건을 모두 만족해야 한다. 판정은 CI(또는 CI 런처가 띄운 평가 배치)만 내리고, 결과는 `ops:metrics`와 체크포인트 매니페스트에 기록한다. 수치는 **초기안**이다. D2에서 판별력(좋은/나쁜 후보를 가르는가)을 측정한 뒤 `referee/GATES.md`에 확정한다(referee-change).

| 조건 | 무엇을 보는가 | 질문 |
|---|---|---|
| A. 수렴 | 학습 곡선 | 더 학습해도 거의 안 바뀌는가? |
| B. 착취 불가 | 최선 응답(BR) 대비 손실 | 누가 이 전략을 노려도 크게 못 이기는가? (GTO의 정의) |
| C. 게이트 | Gate T·S·Q·F·L | 따라 할 수 있고, 둔감하고, 강한가? |
| D. 재현 | 학습 시드 3개 | 운으로 나온 결과가 아닌가? |
| E. 정답 안정 | 체크포인트 간 TP 값 차이 | 학습자에게 줄 정답이 흔들리지 않는가? |

#### A. 수렴 (학습 내부 신호)
- **정책 변화량**: 고정 평가 스팟 세트(환경당 2만 결정, 버전 관리)에서 연속 체크포인트(학습 핸드 10⁷마다 저장) 간 액션 분포 KL 평균 < 0.005, 판단 항목 변화 95백분위 < 2(0–100 척도). 연속 3회 만족.
- **과거 자신과의 대국**: 현재 체크포인트 대 5개 전 체크포인트의 duplicate 대국 차이가 95% CI에 0을 포함(더 이상 확실히 나아지지 않음) — 연속 2회.
- **손실**: TP 헤드 보조 손실(레인지 KL, 스칼라 MSE)이 최근 10% 구간에서 기울기 ≈ 0(선형 회귀 기울기의 95% CI가 0 포함).
- A만으로는 완료가 아니다. 수렴했어도 나쁜 국소해일 수 있으므로(구 RL의 체크/폴드 붕괴, #78) B·C가 필요하다.
- 붕괴 감시: 폴드 비율(베팅을 마주한 결정 기준) > 0.95 또는 레이즈 비율 < 0.02이면 수렴으로 보지 않고 실패로 기록한다.

#### B. 착취 불가 (GTO의 핵심 기준)
"GTO에 가깝다" = 상대가 이 전략을 알고 최선으로 대응해도 얻는 이득이 작다. 환경 크기에 따라 재는 방법이 다르다.

| 환경 | 측정 | 통과 초기안 |
|---|---|---|
| E1 헤즈업 푸시/폴드 | **정확한 BR**: 정책을 고정하고 상대 최선 응답을 직접 계산(`referee/anchors/pushfold.py`의 `ev_loss`, 스택 1~25BB × 앤티 2종) | 등급 고수: 착취 가능성 ≤ 0.03 bb/핸드(내시 앵커 자체 오차 0.01), 초보 ≤ 0.10. 등급별 값은 "복잡성 비용"으로 함께 보고 |
| E2 헤즈업 캐시 | **국소 최선 응답(LBR)**: 결정마다 몇 가지 대안 액션의 기대값을 롤아웃으로 재고 가장 좋은 것을 고르는 공격자(Lisý & Bowling 2017 방식). 공격자가 TP-GTO 상대로 얻는 bb/100 | LBR 이득 95% CI 상한 ≤ 10 bb/100 (참고: 무작위 봇은 수천 bb/100) |
| E3~E5 멀티웨이 | **학습된 공격자(RL-BR)**: TP-GTO를 고정하고, 그것만 노리는 공격자 정책을 정해진 예산(10⁸핸드)으로 학습. 공격자 이득 | 공격자 이득 95% CI 상한 ≤ 5 bb/100(캐시), ≤ 3% ROI(토너먼트). 공격자 예산은 사전 고정 |
| 모든 환경 | **솔버 스팟 대조**: TexasSolver로 풀 수 있는 헤즈업 턴·리버 스팟 세트(버전 관리)에서 TP-GTO 액션의 솔버 대비 EV 손실 | 손실 평균 ≤ 팟의 2%(고수), ≤ 6%(초보) |

- TP 병목이 있으므로 착취 가능성이 0이 될 수는 없다. 그래서 같은 환경의 **병목 없는 기준 정책**(같은 구조에서 액션 헤드가 인코더를 직접 보는 모델)의 착취 가능성도 같은 방법으로 재고, 두 값의 차이를 **복잡성 비용**으로 보고한다. 판정은 절대 기준(위 표) + "기준 정책 대비 착취 가능성이 2배를 넘지 않음"이다.
- 공격자는 TP-GTO를 학습할 때 쓴 적 없는 시드·코드 경로로 돌린다(심판 소유, `referee/exploit/`).

#### C. 게이트 (`referee/GATES.md`)
- Gate T(TP 경유) 100%, Gate L 100%.
- Gate S(둔감성): 버킷 내 섭동에서 판단 항목 변화 95백분위 ≤ 등급 눈금 한 칸, 액션 TV 95백분위 ≤ 0.15, 경계 절벽 ≤ 5%.
- Gate Q(강도): 난이도 1~19 페르소나 필드 전부에 대해 95% CI 하한 > 0. 특히 최상위 페르소나(15~19) 대비 우위. 이론 앵커 손실은 B의 표와 같은 기준.
- Gate F(따라 하기): 사람 수준 TP 오차(초보 σ=20, 중수 12, 고수 6)를 넣은 "따라 하는 봇"이 그 등급의 대상 페르소나 레벨(초보→1~7, 중수→8~14, 고수→15~19)을 95% CI로 이긴다.
- **적응 가치**(정보 누적이 실제로 쓰이는가): 같은 모델에서 게임 내 기억(성향 통계)을 끈 버전 대비, 성향이 뚜렷한 페르소나(스테이션·매니악·나이트) 상대 이득이 95% CI 하한 > 0. 기억을 켜도 이득이 없으면 TP의 `opp.*` 항목을 다시 설계한다.
- **홀드아웃**: 위 평가를 에이전트가 모르는 시드(`HOLDOUT_SEED` Secret)로 한 번 더 돌린다. 공개 시드 결과와 홀드아웃 결과가 95% CI에서 겹치지 않으면 과적합 경보로 완료 불가.

#### D. 재현 (운이 아님)
- 같은 설정·다른 학습 시드 3개로 학습한다. 세 체크포인트 모두 B·C를 통과해야 한다.
- 세 모델의 Gate Q 결과(bb/100·ROI) 95% CI가 서로 겹쳐야 한다. 서비스에는 셋 중 B 점수가 가장 좋은 것을 쓰고, 나머지 둘은 E의 비교 대상으로 남긴다.

#### E. 정답 안정 (가르쳐도 되는가)
- 학습자 채점에 쓰는 값이므로, 정답이 학습 시드나 체크포인트에 따라 크게 바뀌면 안 된다.
- 고정 평가 스팟 세트에서 D의 세 모델 간 판단 항목 값 차이 95백분위 ≤ 등급 눈금 한 칸(초보 25, 중수 10, 고수 3), 주 액션 일치율 ≥ 85%.
- 이 조건을 못 넘는 TP 항목은 그 등급에서 **채점하지 않고**(서비스에 "참고값"으로만 표시) TP v 개정 후보로 올린다.

#### 통계 절차 (모든 판정 공통, GATES "표본 정책")
- 표본 수는 사전 등록한다: 검정력 0.9, α 0.05, 최소 효과 δ를 환경별로 정하고, 파일럿으로 잰 duplicate 블록 SD로 `required_tournaments`/필요 핸드 수를 계산한다.
- 좌석·카드 교환 duplicate 평가, 토너먼트(또는 1,000핸드 블록) 단위 부트스트랩 CI.
- 성공을 위한 조기 중단 금지. 가망이 없을 때만(SPRT 무익성) 중단해 실패로 기록한다. 표본을 다 못 채우면 "판정 불가(표본 부족)"이며 완료가 아니다.

#### 판정 결과와 그 다음
| 결과 | 의미 | 다음 행동 |
|---|---|---|
| 완료 | A~E 모두 통과 | 체크포인트를 `referee/champions/<env_id>/<tier>/`에 등록, ONNX 내보내기, 서비스 정답 교체(문제 은행 재빌드) |
| 수렴했지만 B·C 실패 | 국소해 또는 병목 한계 | 상대 풀·탐색(엔트로피) 조정 실험, 그래도 실패하면 TP 항목·눈금 재검토(ADR) |
| B 통과, E 실패 | 강하지만 정답이 흔들림 | 둔감성 정규화 강화, 흔들리는 항목은 채점 제외 |
| 판정 불가 | 표본 부족 | 예산 내 표본 확대 또는 δ 재검토(ADR) |

- **재학습 조건**: TP 명세 버전이 바뀜, 환경 축이 추가됨, 엔진 규칙이 바뀜(Gate R 명세 변경), 또는 새 공격자가 기존 챔피언을 기준 이상으로 착취함. 재학습한 모델은 기존 챔피언과 duplicate 대국에서 비열등(95% CI 하한 > −δ)이어야 교체된다.
- 서비스 표시: 정답 화면에 "TP-GTO `<env_id>` `<tier>` v`<n>`, 착취 가능성 ≤ X"를 작게 표시해, 학습자가 어떤 기준의 정답인지 알 수 있게 한다.

### 4.4 화면 상세

**Training Game**
- 레이아웃: 노트북 1440px 기준 테이블 영역 약 1fr + TP 패널 392px. 태블릿 가로도 같은 배치(패널 340px). 폰 세로는 테이블 3:4 + 바텀 시트(접힘 78px, 펼침 최대 72vh, 내 차례에 자동 펼침).
- 템포: 다른 좌석 1.5초(설정 0.8/1.5/2.5초), 딜링 카드당 80ms 간격·이동 380ms, 칩 이동 500ms, 쇼다운 공개 250ms 간격, 핸드 사이 1.6초.
- 상태: 대기(행동 중 표시·직전 채점 결과·핸드 기록) → 내 차례(TP 질문 목록 + 액션) → 제출(채점 결과, 액션 즉시 반영, 게임 계속).
- TP 패널 내용: 상황 칩(스트리트·포지션·유효 스택·팟·콜 금액·SPR), 판단 대상 상대(관측 핸드 수), 단계 묶음 B→C→D→E→F, 등급별 항목(`docs/TP.md` §3).
- "정보 부족": 대상 상대 관측 핸드 < n(명세 상수)이면 성향 항목은 입력·채점하지 않는다.
- 게임 끝: 토너먼트는 탈락·우승, 캐시는 M 핸드. 게임 요약(TP 항목별 점수, 가장 큰 손실 결정 3개, 학습 추천).

**채점 (`tp/grade.ts`)**

| 항목 종류 | 점수 |
|---|---|
| 스칼라(0–100) | 오차 ≤ 허용(등급 눈금 반 칸)이면 100, 아니면 100 − (오차 − 허용) × 2.4, 0 하한 |
| 레인지 | 초보·중수: 상위 X% 오차를 스칼라처럼. 고수: 콤보 가중 자카드 × 100 |
| 계산 항목 | 두 점수: ① 사용자 입력 앞 단계로 다시 계산한 값과 비교(계산 실수) ② TP-GTO 값과 비교(판단 전파). 약점은 ①이 낮으면 해당 항목, ②만 낮으면 앞 단계 항목에 기록 |
| 액션 | 정책 확률 비(선택 확률 / 최대 확률) × 100, 그리고 EV 손실(bb) 보고(D3, 가치 헤드) |

**학습 섹션**
- 문제 생성기: 항목 × 난이도마다 함수 하나(`generators/<item>.ts`). 정답은 D1~D2는 JS 몬테카를로, D3부터 사전계산 문제 은행(오라클 값) + 모델.
- 출제: 약점 가중(최근 20문제 평균이 낮은 항목 3배 가중) + 간격 반복(틀린 유형은 1·3·7일 뒤 다시).
- 피드백: 정답·내 답 막대 비교, 한 줄 설명(규칙 기반 문장), "왜"를 보는 펼침(레인지 그림·에퀴티 분포).

**복기**
- 입력: 카드 피커(52장 그리드), 포지션·스택, 스트리트별 액션 타임라인(좌석·액션·사이즈를 칩으로 추가), 또는 핸드 기록 텍스트 붙여넣기(D4: 주요 사이트 형식 파서, 개인 기록 전용).
- 분석: 결정 지점마다 TP-GTO의 TP 값과 액션 혼합, 사용자 액션 점수, "가장 크게 갈린 판단".
- 비슷한 상황 생성: 같은 핸드 클래스·같은 보드 텍스처 군(페어드·모노톤·연결성)·같은 스택 버킷으로 시드를 만들어 Training Game 시작(데모는 무늬만 바꾸는 방식).
