# 레인지 벡터 CFR + TP 제약 (GPU) — 연구 노트 (#393)

- 원 제안(소유자, 2026-10-30, 번역): "GTO Wizard 같은 솔버는 플레이어마다 모든 핸드 콤보(무늬 포함) × 상황(프리플랍 오픈, 몇 배 2벳을 마주함 …)의 행렬을 들고, 각 핸드가 몇 %로 오픈·폴드하는지 정한다. 게임은 모든 플레이어의 행렬로 진행된다. GPU를 잘 쓸 것이다. TP와 함께 적용하는 방법을 연구해라."
- 수치는 모두 **로컬 참고값**(Windows 노트북 1코어, numpy, 판정 근거 아님)이다. 판정 근거는 CI뿐이다(CLAUDE.md).
- 코드: `stalker/vcfr/river.py`(헤즈업 리버 공개 트리·O(n) 쇼다운), `stalker/vcfr/solver.py`(벡터 CFR+, per-combo형·TP key형, 정확한 최선 응답), 테스트 `tests/test_vcfr.py`.

## 0. 요약
1. 소유자가 말한 것은 **공개 트리 위 레인지 벡터 CFR**(vector-form CFR)이다. 전략은 공개 노드마다 1326 × 액션 텐서이고, 한 번의 트리 순회로 모든 콤보를 정확한 레인지 가중치로 갱신한다. 터미널 값은 핸드 대 핸드 쇼다운 행렬과 상대 도달 벡터의 곱이다. 공개 솔버(postflop-solver·TexasSolver)가 이 방식이고, 상용 솔버(PioSOLVER·GTO Wizard 등)도 같은 계열로 알려져 있다(내부는 비공개, 확인 못 함).
2. **TP 제약과 그대로 결합된다.** 콤보 i의 노드 h 전략을 π(a | key(h, i))로 두고, 후회값을 콤보에서 key로 scatter-add, 전략을 key에서 콤보로 gather하면 된다. 고정된 공개 서브게임 안에서 딜 샘플링 없이 레인지 정확한 추상화 CFR 갱신이다(이 프로토타입은 헤즈업 리버라 찬스·액션을 모두 전개한다. 미래 보드나 공개 액션을 샘플링하면 그만큼 표본 잡음이 남는다). 같은 코드에서 key = 콤보이면 제약 없는 해가 나오고, 그 차이가 **TP 비용**이다(#359의 기준 전략이 공짜로 생긴다). 프로토타입에서 key = 콤보 경로가 per-combo 해와 비트 단위로 같음을 테스트했다.
3. **새 발견(가장 중요): TP 특징을 "이번 반복의 레인지"로 계산하면 수렴하지 않는다.** 리버 장난감에서 `hand.equity` 단계를 현재 전략의 상대 레인지에 대해 계산하면(E3 MCCFR가 지금 하는 방식) 착취 가능성이 반복할수록 **커진다**(17단계: 100회 2.8% → 1000회 10.5% 팟, 실전 메뉴 300회 7.4%). 같은 key를 **평균 전략의 레인지**(서비스되는 정책이 실제로 쓰는 레인지)에 대해 10회마다 다시 계산하면 0.5% 팟(실전 메뉴 1.0%)에서 멈춘다. E3에도 같은 구조가 있어 #391(BTN AQs 림프)과 LBR에 영향을 줄 수 있다. E3 실험 이슈로 가장 먼저 확인할 것을 추천한다(§6 V1).
4. 부수 발견: E3 방식의 공개 key 합치기(팟 오즈 단계·레이즈 수·합법 액션)는 실전 리버 메뉴에서 착취 가능성 24–27% 팟으로 무너진다. 큰 벳들(1.5팟·2팟·올인)이 한 표를 쓰기 때문이다. 결합 key(ADR 0019 단계 C)에 **마주한 벳 크기 버킷**을 넣어야 한다.
5. 6인 실전 메뉴(#382)의 전체 공개 트리는 벡터 형식으로도 매 반복 전부 돌 수 없다. 첫 쓸모 있는 범위는 **헤즈업 포스트플랍 서브게임**(TP 비용·#359 기준, 무료 CPU)과, 그다음 **공개 찬스·공개 액션을 샘플링하는 벡터형 MCCFR**(GPU, E3 학습기의 대체 후보)이다. 6인 프리플랍 전체 벡터 CFR은 플랍 가치 근사가 필요해 연구 단계로 둔다.
6. GPU는 지금 **필요 없다**. 리버 서브게임은 numpy CPU로 충분하다(턴은 미측정, 분 단위 예상). GPU 단계(V3)에 가면 PyTorch를 선택적 의존성(`[gpu]`)으로 두고, RunPod 커뮤니티 RTX 4090($0.34/h)으로 월 $100 상한 안에서 시험한다.

## 1. 솔버식 벡터 CFR은 어떻게 작동하나

### 1.1 공개 트리와 레인지 벡터
- 포커의 상태 = 공개 상태(보드, 액션 이력, 팟·스택) + 각 플레이어의 비공개 카드. 베팅 트리는 홀카드와 무관하므로 **공개 트리 하나**에 모든 핸드가 함께 산다.
- 노드 h에서 플레이어 p의 도달 확률을 콤보마다 둔 벡터 r_p(h) ∈ ℝ^1326가 그 노드의 **레인지**다. 루트 레인지에 p의 전략 σ_p(a | h, i)를 곱하며 내려간다: r_p(ha)_i = r_p(h)_i · σ_p(a|h,i). 이것이 "플레이어가 행렬을 들고 온다"의 정확한 의미다.
- 반사실 가치(counterfactual value)도 벡터다: v_p(h)_i = Σ_z π_{-p}(z) u_p(z) (상대 도달만 가중). 터미널에서
  - 쇼다운: v_p(i) = c · Σ_j valid(i,j) · sign(s_i − s_j) · r_{-p}(j) (c = 각자 넣은 칩, valid = 카드 겹침 없음). 즉 **쇼다운 행렬 W(1326×1326) × 상대 레인지 벡터**다.
  - 폴드: v_p(i) = ±c · Σ_j valid(i,j) · r_{-p}(j).
- 행렬을 실제로 만들 필요는 없다. 강도로 한 번 정렬한 뒤 누적합(이기는 쪽 질량, 지는 쪽 질량)을 구하고, 카드 제거는 카드별 같은 누적합을 빼면 된다(포함-배제: 두 장이 다 겹치는 콤보는 나 자신, 무승부). 정렬 뒤 O(n)이다. 프로토타입 `Showdown.less_greater`가 이 방식이고, 조밀 행렬 계산과 1e-9 이내로 같다(`test_showdown_kernel_matches_dense_matrix`). 이 기법은 Johanson 외(2011, "Accelerating Best Response Calculation in Large Extensive Games")의 터미널 계산으로 알려져 있다 — **이번 세션에서 원문은 읽지 못했다**(기억에 근거, 확인 필요). PCS 논문 초록은 "터미널 계산을 O(n²)에서 O(n)으로 줄인다"고 적는다(아래 출처).

### 1.2 후회 텐서와 갱신
- 결정 노드 h(플레이어 q)마다 후회 R_h ∈ ℝ^{1326×A}, 평균 전략 합 S_h ∈ ℝ^{1326×A}. 한 반복에 트리를 플레이어마다 한 번 돌며 (교대 갱신):
  - q가 갱신 중인 플레이어면 자식 가치 V ∈ ℝ^{1326×A}, 노드 가치 v = Σ_a σ ⊙ V, R_h += V − v·1ᵀ (CFR+는 0 아래를 자름), S_h += t · r_q ⊙ σ (선형 평균).
  - 아니면 r_q를 액션마다 σ로 나눠 자식으로 내려보내고 자식 가치를 더한다.
- 모든 연산이 (콤보 × 액션) 원소별 연산과 정렬된 누적합이라 GPU 배치에 맞는다. Kim(2024)은 CFR 전체를 레벨별 행렬·희소 행렬 연산으로 바꿔 CuPy로 GPU에서 돌렸고, 큰 게임에서 OpenSpiel C++ 대비 최대 약 114배를 보고했다(RTX 4090, 메모리는 더 씀).
- 수렴 가속: CFR+(Tammelin 2014; Bowling 외 2015, 헤즈업 리밋 홀덤을 풂), DCFR(Brown·Sandholm 2019, CFR+보다 모든 시험 게임에서 같거나 나음). postflop-solver는 DCFR(γ=3)과 4의 거듭제곱마다 평균 전략 초기화를 쓴다(README).

### 1.3 카드 동형(무늬 대칭)
- 보드가 무늬 대칭을 가지면(예: 모노톤 플랍이면 플랍에 없는 세 무늬는 서로 바꿔도 같다) 그 무늬를 바꾼 턴·리버 카드는 전략상 같다. postflop-solver는 이 동형 딜을 합친다(모노톤 플랍이면 남은 세 무늬 중 둘을 건너뜀, README). 프리플랍은 1326 → 169 클래스로 줄지만, 포스트플랍에서는 보드가 대칭을 깨므로 콤보 벡터는 1326(보드 제외 1081–1225)으로 두고 **찬스 노드만** 합치는 것이 표준이다.
- 우리 TP key는 원래 무늬를 직접 보지 않는다(hand.equity·board.nut 등 값만). 그래서 동형 합치기는 key 표에는 영향이 없고, 찬스 노드 순회 수만 줄인다.

### 1.4 큰 게임: 서브게임·깊이 제한
- DeepStack(Moravčík 외 2017): 매 결정마다 현재 공개 상태에서 서브트리를 다시 푼다(continual re-solving). 미래 라운드 값은 레인지 벡터를 입력받아 콤보별 반사실 가치 벡터를 내는 신경망(counterfactual value network)으로 대신한다. 1천만 개 무작위 상황을 CFR로 풀어 학습했다(1807.00900 요약 기준).
- Modicum(Brown·Sandholm·Amos 2018): 깊이 제한 해법. 경계에서 상대가 여러 연속 전략 중 고르게 해 리프 값을 강건하게 만든다. 4코어 CPU·16GB로 당시 최강 봇들을 이겼다.
- ReBeL(Brown 외 2020): 공개 믿음 상태(PBS = 공개 상태 + 모든 플레이어의 레인지) 위에서 가치·정책 신경망을 자기 대국으로 학습하고 서브게임은 CFR로 푼다. 2인 제로섬에서 내쉬 수렴을 증명한다.
- 공통점: **모두 2인 제로섬**이다. 6인에는 이론 보장이 없고, Pluribus(2019)는 6인에서 샘플링 MCCFR 청사진 + 실시간 탐색을 썼다(이번 세션에서 원문 확인 안 함).

### 1.5 샘플링과의 관계
- Johanson 외(2012, PCS): **모든 플레이어가 보는 공개 찬스(보드)만 샘플링**하고 비공개 카드는 벡터로 전부 다루면, 반복은 느리지만 정확해지고 큰 포커 게임에서 찬스 샘플링 CFR보다 빨리 수렴한다(초록). 지금 E3는 정반대 끝(딜 하나 샘플, 외부 샘플링)이다.
- 벡터형 MCCFR(공개 액션도 샘플링): 상대 노드에서 레인지 평균 확률 q(a) = Σ_i r(i)σ(a|i) / Σ_i r(i)로 액션 하나를 뽑고 r'(i) = r(i)σ(a|i)/q(a)로 내려보내면 기대값이 보존된다. 특허 문서(Ant Group 계열 "Determining action selection policies of an execution device", 벡터형 MCCFR, 샘플링 정책 RCS·MCS·WCS·WAS)가 이 계열을 적는다. **2차 출처이고 논문 원문(Li 외)은 이번 세션에서 확인하지 못했다.**

## 2. TP와 결합: TP 제약 벡터 CFR

### 2.1 정의
- 노드 h, 행동 플레이어 q, 콤보 i의 TP key = (공개 TP 사실(h), TP 판단 단계(h, i)). 공개 사실 = 좌석·스트리트·상대 수·레이즈 수·팟 오즈·SPR·합법 액션(E3 `public_key`). 판단 단계 = `hand.equity`(상대 공개 레인지 대비 에퀴티의 분위 단계), 앞으로 #389의 `hand.outs`·`hand.vuln`·`hand.block`·`board.adv` 등.
- 벡터 형식에서는 **노드마다 TP 특징을 콤보 텐서로 한 번에 계산**한다: eq = Showdown.equity(r_{-q}) ∈ ℝ^n (O(n)), outs/vuln은 다음 카드별 에퀴티 변화(턴·플랍, 카드 48장 × O(n)), block은 상대 밸류 레인지와 내 카드의 카드 질량(O(n), `card_mass`와 같은 bincount). 결과는 콤보별 정수 key 행 번호 k(h, i).
- 갱신: 후회 표 T[key] ∈ ℝ^{A}. R 갱신은 `np.add.at(T, k(h,·), V − v)`(scatter-add), 전략은 `σ(h, i) = RM(T)[k(h, i)]`(gather), 평균 전략 합도 r_q 가중으로 scatter-add. 공개 TP 사실이 같은 노드들은 같은 표를 쓴다(`tp_keyer(k, public="tp")`).
- 이것은 **추상화 CFR(abstraction CFR)을 정확한 레인지 가중치로 돈 것**이다. 딜 샘플링 분산이 없다. 지금 E3(외부 샘플링, 딜 하나)와 같은 고정점을 노리되 반복마다 1326² 핸드 쌍 정보를 다 쓴다.

### 2.2 정확성: 무엇이 보장되고 무엇이 아닌가
- 제약 없는 per-combo 형: 2인 제로섬 서브게임에서 CFR+ 평균 전략은 내쉬로 수렴한다(완전 기억). 프로토타입에서 1000회 후 착취 가능성 0.017% 팟.
- TP key 형: 여러 (노드, 콤보)를 하나의 정보 집합으로 합치므로 **완전 기억이 깨진다**. CFR의 일반 보장은 없다. Lanctot 외(2012)는 특정 부류의 불완전 기억 추상화(같은 key로 합쳐진 상태들의 미래 구조·보상이 비슷한 경우)에서 원 게임에 대한 후회 상한을 보였다 — 합쳐진 상태가 얼마나 다른가에 비례하는 항이 붙는다. TP key는 "같은 TP 판단 = 같은 행동"이라는 제약이므로 그 항이 곧 **TP 비용**이다. 보장되는 것: 고정된 key 함수 아래에서 추상 게임의 후회는 줄어든다(추상 게임이 잘 정의될 때).
- **key가 전략에 의존하면 추상 게임 자체가 움직인다.** hand.equity는 상대 *공개 레인지* 대비이고, 레인지는 상대 전략에 따라 바뀐다. 반복마다 key 배정이 바뀌면 "key v의 후회"가 매번 다른 콤보 집합의 후회 합이 되고, 평균 전략은 서로 다른 의미의 key를 섞는다. 이 경우 위의 상한도 적용되지 않는다. 측정(§4)에서 이 차이가 크게 나왔다.
- 지금 E3가 보장하는 것: 없다(`stalker/e3/mccfr.py` 독스트링도 그렇게 적는다). 수렴은 LBR·필드로 경험적으로만 본다. 그리고 E3의 key는 `_seat_probs`가 **현재 후회 매칭 전략**으로 갱신한 레인지에서 계산한다 = 아래 "current" 형이다.
- 해결 방향(프로토타입에서 확인): key를 계산하는 레인지를 **평균 전략의 레인지로, 주기적으로(10회마다) 갱신**한다("average" 형). 서비스되는 정책은 평균 전략이고, 서비스 시점에 key는 그 정책 자신의 공개 레인지로 계산되므로(정보 계약, TP.md §2) 학습과 서비스가 같은 key 의미를 쓴다. 평균 전략은 천천히 움직여 key 배정이 안정된다(촘촘한 key에서는 완전히 고정되지는 않는다, §4 해석 4).

### 2.3 메모리
- per-combo 표: 노드 수 × 1326 × A × 4B × 2(후회·평균). 리버 실전 메뉴(84 결정 노드, A≈6–10) 약 5–7MB. 턴 서브게임(리버 48장 열거)은 GB 단위, 플랍 서브게임 전체는 수백 GB(§3.2).
- TP key 표: key 수 × A × 8B. E3 고수 표 20만 key라도 약 15MB다. **TP 제약 벡터 CFR의 저장량은 노드 수가 아니라 key 수에 비례한다.** 노드별 콤보 벡터는 순회 중 경로상에만 있으면 된다(깊이 × 1326 × A, 수 MB). 그래서 TP key 형은 공개 트리가 커도 메모리 문제가 없고, 문제는 **반복당 연산**뿐이다.

### 2.4 반복당 연산
- 노드당: 전략 gather(n×A), 자식 레인지 n×A, 가치 합 n×A, 후회 scatter n×A, TP 특징 계산(리버 equity O(n), 플랍·턴은 런아웃 수 × O(n)). 터미널: O(n) 누적합 2벌.
- 프로토타입(1코어 numpy, §4): 결정 노드 14개 리버 트리에서 per-combo **약 130–195 it/s**, TP key 형 약 55–90 it/s(key 계산의 정렬·unique가 추가 비용). 실전 메뉴 84개 노드에서 per-combo 29 it/s, TP key 형 약 12 it/s. 노드·반복당 약 0.2–0.5ms이고 대부분 파이썬 호출 오버헤드다(n=1081은 GPU에 작다).
- GPU에서는 노드 하나의 n=1326 연산은 너무 작아 커널 실행 오버헤드(수 µs)가 지배한다. **배치 축이 필요하다**: 같은 공개 베팅 트리를 쓰는 B개의 보드(공개 찬스 샘플)를 한 텐서 (B, 1326, A)로 묶고 트리 레벨 단위로 돈다. 베팅 트리는 보드와 무관하므로 B개 보드가 같은 트리 구조를 공유한다. B=1024면 노드당 약 10⁷ 원소로 GPU 대역폭을 채운다.

## 3. 6인 실전 메뉴(#382)에서의 타당성

### 3.1 공개 트리 크기
- E3 프리플랍 공개 트리(결정 노드 = 경로 수, 로컬 정확 계수): 헤즈업 v1 16개, **헤즈업 real 1,000개**. 6인 v1 **289,036개**(플랍 도달 리프 2인 113,607 · 3인 110,290 · 4인 51,920 · 5인 12,065 · 6인 1,123).
- 6인 real 프리플랍: 정확 계수는 로컬 메모리(6GB 넘음)로 멈췄다. Knuth 무작위 탐침 추정(20만 경로, 표준오차 포함, 꼬리가 두꺼워 과소 추정 쪽)은 **약 1.8×10⁷ 결정 노드**(±1.6×10⁶), 플랍 도달 리프 약 1.9×10⁷개(2인 7.0×10⁶ · 3인 8.3×10⁶ · 4인 3.3×10⁶ · 5인 5.8×10⁵ · 6인 1.1×10⁵)다. 같은 추정기는 v1에서 27만(±2.7만)으로 정확값 28.9만과 맞았다. 즉 **실전 메뉴는 6인 프리플랍만 v1의 약 60배**다. per-combo 표로 저장하면 1.8×10⁷ × 1326 × A(≈10) × 8B ≈ 1.9TB다.
- 헤즈업 리버 한 스트리트(1팟, 스택 2팟, real 벳 8종 + 레이즈 6종 + 올인, 레이즈 상한 3): 결정 노드 84 · 전체 노드 249(`RiverGame`). 스택이 깊을수록 더 많은 사이즈가 남아 커진다.
- 결론: **6인 real 전체 공개 트리를 매 반복 순회하는 것은 벡터 형식으로도 불가능하다**(프리플랍만으로 v1의 수백 배 이상, 그 뒤에 플랍 22,100 × 턴 49 × 리버 48 찬스와 스트리트마다의 베팅 트리).

### 3.2 그래서 무엇을 줄이나
| 방법 | 줄이는 것 | TP와의 관계 | 비용 |
|---|---|---|---|
| 공개 찬스 샘플링(PCS) | 보드를 반복마다 B개 샘플 | 그대로 | 분산 소폭, GPU 배치 축이 됨 |
| 공개 액션 샘플링(벡터형 MCCFR, §1.5) | 비갱신 플레이어 노드에서 액션 1개 | 그대로 | 분산. E3 외부 샘플링과 같은 구조, 대신 딜 대신 레인지 전체 |
| 깊이 제한 + 가치 함수(DeepStack·Modicum·ReBeL) | 다음 스트리트 이후를 가치 근사로 | 리프 가치는 TP와 무관하게 계산 가능(내부 방법 제약 없음, 헌장 요구 1) | 가치망 학습 = GPU, 2인 제로섬만 이론 근거 |
| 서브게임 해법(헤즈업 포스트플랍) | 루트를 플랍/턴/리버의 한 공개 상태로 | TP 비용 측정·교사에 적합 | CPU로 충분 |
| 사이즈 추상화 | — | **소유자 결정으로 금지**(#382: 실전 사이즈는 줄이지 않는다) | — |

- 사이즈 메뉴는 줄일 수 없으므로(#382) 줄이는 축은 **찬스 샘플링·액션 샘플링·깊이 제한**뿐이다. TP key는 이 셋과 모두 양립한다.
- 3인 이상 쇼다운: 벡터 형식의 터미널은 상대 둘 이상의 결합 분포가 필요하다(정확하면 O(n^k)). 지금 `tp_key.multi_equity`처럼 상대끼리 카드 제거를 무시하는 독립 근사를 쓰면 O(k·n)이다. 이 근사는 승자 판정(누가 모두를 이기나)에서 정확하지 않으므로, 멀티웨이 터미널은 "독립 근사 + 정확한 샘플 딜 검증"을 같이 둔다.
- 6인에는 균형 보장이 없다. 그래서 강도 판단은 지금처럼 LBR·필드·최악 손실(ADR 0015)로만 한다.

### 3.3 첫 쓸모 있는 범위
1. **헤즈업 포스트플랍 서브게임 라이브러리(무료 CPU).** E3 자기 대국에서 헤즈업으로 리버·턴에 간 공개 상태(보드, 두 공개 레인지, 팟·스택)를 수십 개 뽑아 per-combo로 정확히 푼다. 같은 상태를 TP key 형으로 풀어 **스팟별 TP 비용**(착취 가능성 차이, 맞대결 EV)을 낸다. #359의 "TP 없는 기준"을 서브게임 수준에서 가장 싸게 주는 방법이다. 리버는 1코어로 초 단위, 턴은 numpy로 분 단위가 예상된다(턴 미측정).
2. **E3 key 레인지 수정 실험(무료 CI).** §2.2 발견을 E3에 옮긴다: `_seat_probs`·equity step을 현재 전략이 아니라 평균 전략 레인지로(주기 갱신). 10⁵회 CI로 LBR·필드·#391 행을 비교.
3. **벡터형 MCCFR 학습기(GPU, 연구).** 헤즈업 real 전체 게임부터. 성공하면 6인으로.
4. **6인 프리플랍 전용 벡터 CFR + 플랍 가치 근사.** 6인 v1 프리플랍 28.9만 노드 × 1326 × A(≈3) × 8B ≈ 9GB(per-combo), TP key 형이면 표는 MB 단위. 플랍 리프 가치를 "팟 × 에퀴티(실현율 보정)"나 E3 포스트플랍 정책의 평가로 근사하면 #391 같은 프리플랍 이상을 잡는 **프리플랍 교사·검사기**가 된다. 실전 메뉴 트리는 그보다 훨씬 커서(§3.1) 샘플링이 필요하다. 연구 단계.

해석:
1. **per-combo 벡터 CFR+는 빠르게 균형으로 간다**(작은 메뉴 1000회 0.017%, 실전 메뉴 300회 0.22% 팟). 이것이 #359 기준의 서브게임 판이다. 반복마다 1,081² 핸드 쌍을 정확히 다루므로 딜 샘플링 분산이 없다.
2. **TP 비용은 key 해상도와 함께 줄어든다**(average 형, 작은 메뉴 1000회): 5단계 1.8%, 11단계 0.66%, 17단계 0.51% 팟. 맞대결 손실은 −0.60 / −0.20 / −0.13% 팟. 리버에서 hand.equity 단계가 놓치는 것은 같은 단계 안의 블로커 차이(어떤 콤보로 블러프·콜하나)와 단계 안 강도 차이다. #389의 `hand.block`이 이 차이를 줄일 것으로 예상한다 — 다음 측정 대상.
3. **current 형(E3 방식)은 반복할수록 나빠진다**, 그리고 key가 촘촘할수록 더 나쁘다(17단계 10.5%, 50단계 13.5% 팟). current 형의 *현재* 전략은 착취 가능성 30–50%에서 진동했다(별도 실행, 참고). key 의미가 전략과 함께 움직이는 되먹임이다. 맞대결 EV 손실은 작아(−0.19%) 균형 상대나 필드에는 잘 안 보이지만 최선 응답에게는 크게 착취당한다. LBR·필드가 #391 같은 이상을 놓치는 이유와 같은 모양이다(가설, E3에서 확인 필요).
4. average 형도 완전히 고정되지는 않는다: 50단계는 100회 0.58% → 1000회 1.18%로 다시 올랐다. 별도 실행(참고)에서 key를 서브게임 시작 레인지로 고정한 "initial" 형은 17단계 0.58%, 50단계 0.32%로 안정했다. 리버 서브게임에서는 initial이 가장 깨끗하지만, 전체 게임에서는 "시작 레인지"가 곧 앞 스트리트 전략이라 같은 문제가 한 단계 위로 옮겨 간다. 전체 게임 처방은 average(느리게 움직이는 레인지) + 갱신 주기·key 해상도 측정이다.
5. **공개 사실을 E3 방식으로 합치면(-public) 실전 메뉴에서 크게 무너진다**: 24–27% 팟(작은 메뉴에서는 0.7–3%). 이 리버에서 팟 오즈 단계(≥40% 한 칸)와 레이즈 수가 같으면 1.5팟 벳·2팟 벳·올인에 대한 응답이 하나의 표를 쓰고, 그 노드들은 상대 레인지가 전혀 다르다. 실전 사이즈(#382)를 넣은 결합 key(ADR 0019 단계 C)는 **마주한 사이즈 버킷**(TP.md §6 벳 크기 버킷)을 공개 key에 넣어야 한다는 신호다. 지금 E3 key는 팟 오즈 단계와 합법 액션 문자열만 본다.
6. key 계산이 반복당 시간을 약 2–2.5배로 늘린다(정렬·unique). GPU로 가면 강도 순서를 보드당 한 번 미리 정렬하고(레인지와 무관) 분위 단계를 누적합으로 바꿀 수 있다.

## 5. GPU 계획
- **라이브러리**: 프로토타입은 numpy 그대로 둔다(CI 기준). GPU 단계에서 **PyTorch를 선택적 의존성 `[gpu]`** 로 추천한다. 이유: `index_add_`/`scatter_add_`·`gather`·`cumsum`·`searchsorted`가 다 있고, CPU에서도 같은 코드가 돌아 CI가 GPU 없이 검사할 수 있으며, 깊이 제한 단계의 가치 신경망(E5, ADR 0017 §5)도 같은 라이브러리를 쓴다. CuPy는 numpy 그대로라 이 프로토타입을 옮기기엔 가장 쉽지만(Kim 2024가 CuPy) 신경망이 없다. JAX는 jit가 강하지만 Windows GPU 지원이 약하고 동적 트리에 불편하다. numba 선택 커널(ADR 0013)처럼 **없으면 numpy로 떨어지는** 구조로 둔다. 새 의존성은 그 단계 PR에서 이유를 적는다(CLAUDE.md).
- **VRAM**(fp32, 후회+평균):
  - 헤즈업 리버 per-combo, 실전 메뉴: 약 5–7MB. 4GB MX570에서도 충분.
  - 헤즈업 턴 서브게임 per-combo(리버 48장 × 리버 트리 84, 턴 트리 연속 리프 약 20 가정): 약 8만 노드 × 1326 × 7 × 8B ≈ 6GB → 24GB급 GPU.
  - 헤즈업 플랍 서브게임 per-combo 전부 열거: × 49 ≈ 300GB → 불가. PCS 샘플링 + TP key 표면 표는 MB, 작업 텐서는 배치 B × 깊이 × 1326 × A ≈ B=1024에서 수백 MB.
  - TP key 형 전체 게임(벡터형 MCCFR): 표 ≤ 100MB, 작업 텐서 수백 MB–수 GB(배치 크기로 조절). 24GB면 넉넉하다.
- **RunPod 가격**(공식 가격 페이지, 2026-10-30 조회, 커뮤니티/보안): RTX 3090 $0.22/$0.50, RTX A5000 $0.16/$0.27, A40 $0.35/$0.59, **RTX 4090 $0.34/$0.89**, L4 $0.44/$0.59, L40S $0.79/$1.09, RTX 5090 $0.69/$1.19, A100 80GB PCIe $1.19/$1.79, H100 PCIe $1.99/$2.89. 가격은 자주 바뀐다.
- **예산**: 월 $100 상한(ADR 0017, `harness/budget.json`)에서 4090 커뮤니티는 약 290시간이다. ADR 0019의 CPU 체인 계획이 이미 상한을 넘는 중간값을 잡고 있으므로(NH-9 대기), GPU 시험은 **1회 2–4시간, 월 10–20시간($4–7)** 으로 시작한다. 상한 변경은 소유자 결정이다. 지금 하네스의 파드는 CPU flavor만 쓰므로 GPU 파드는 launcher 확장(harness-change)이 필요하다.
- 처리량 기대(추정, 미측정): 노드·보드당 1326 × A 원소 연산 수십 회 → 4090 메모리 대역폭(약 1TB/s) 기준 보드 1,024개 배치의 리버 트리 한 번에 수 ms. 실제 수치는 V3 게이트에서 잰다.

## 6. 단계별 계획 (측정 가능한 게이트)
| 단계 | 내용 | 비용 | 게이트(합격선) |
|---|---|---|---|
| V0 (이 PR) | numpy 헤즈업 리버 벡터 CFR+, per-combo·TP key 두 형, key 레인지 3종 | $0 | 테스트 통과, per-combo 착취 < 0.5% 팟, key=콤보 경로 비트 동일 |
| V1 | **E3 key 레인지 실험**: equity step(및 `_seat_probs`)을 평균 전략 레인지로(N회마다 갱신). E3 중수 10⁵회 CI 4시드, 기존 대비 | 무료 CI | LBR(평균 전략) 기존 이하, 필드 최악 ≥ 0 유지, #391 BTN 퍼스트인 행에서 림프 비율 출력 |
| V2 | 헤즈업 서브게임 라이브러리 + TP 비용 지표: E3 자기 대국에서 헤즈업 리버·턴 스팟 50개, per-combo vs 등급별 TP key(#389 항목 포함) | 무료 CPU | 기준 착취 < 0.5% 팟, 스팟별 TP 비용 분포(중앙값·90%) 보고. #359 ADR 입력 |
| V3 | GPU 포팅(PyTorch `[gpu]`, numpy 대체 경로 유지), 보드 배치 PCS, 헤즈업 플랍 서브게임 TP key 형 | 파드 2–4h, $1–2/회 | CPU 결과와 1e-5 이내 일치, 같은 서브게임 CPU 대비 ≥ 50배 처리량 |
| V4 | 벡터형 MCCFR 학습기(공개 액션 샘플링), 헤즈업 real 전체 게임 | 파드 월 10–20h | 같은 파드 비용에서 E3 MCCFR 대비 LBR 낮음(헤즈업) |
| V5 | 6인 확장 또는 6인 프리플랍 교사(플랍 가치 근사) | V4 결과로 산정 | 같은 비용에서 E3 6인 체인 대비 LBR·필드 우위, 아니면 중단 |

- **ADR 0019와의 관계**: ADR 0019(#390, 작성 중)는 E3 MCCFR(CPU 파드) 결합 key 체인 한 번을 계획한다. 이 노트는 그 계획을 바꾸지 않는다. 다만 **V1은 결합 key 체인(단계 C) 전에 끝내야 한다.** key 레인지 방식이 바뀌면 key 의미가 바뀌어 체인을 다시 돌려야 하기 때문이다(ADR 0019 §3.2 표의 "B key 항목 추가"와 같은 재학습 이유). V1은 무료 CI라 예산에 영향이 없다. V2는 #359 ADR의 기준 전략 설계에 서브게임 선택지로 넣는다. §4 해석 5(마주한 벳 크기 버킷이 공개 key에 없으면 실전 메뉴에서 무너짐)는 단계 C 결합 key 설계(#389·후속 ①)의 입력이다. V2 서브게임 라이브러리로 버킷 경계를 같이 잴 수 있다. V3 이후의 GPU 비용은 ADR 0019 §5 월별 표에 없는 새 항목이고, V3 게이트 결과로 E3 체인을 대체할지(돈을 아낄지) 판단한다.

## 7. 열린 질문 (소유자)
1. GPU 시험 예산: 월 $100 상한 안에서 GPU 파드 월 10–20시간($4–7)을 써도 되는가(V3부터). 하네스에 GPU 파드 지원을 넣는 harness-change가 필요하다.
2. 기준(#359)을 "헤즈업 서브게임의 정확한 per-combo 해"로 시작해도 되는가, 아니면 6인 전체 게임의 TP 없는 기준이 꼭 필요한가(후자는 V4–V5 이후).
3. V1 결과가 좋으면 ADR 0019 단계 C 결합 key 체인을 V1 방식으로 돌리는 것에 동의하는가.
