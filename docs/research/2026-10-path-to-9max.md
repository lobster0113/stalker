수치 기준은 첫 제안값이다. 각 단계 첫 CI 측정 뒤 ADR로 확정한다. 모든 판정은 CI 산출 수치만 쓴다(CLAUDE.md).

E3를 9인보다 먼저 하는 이유: 다인 포스트플랍의 새로운 문제(누가 공격자인가, 멀티웨이 팟, 포지션 2개 이상)는 6인에서 모두 생기고, 트리는 9인의 대략 2/3 깊이라 반복 처리량이 1.5배 이상이다.

## 3. 핵심 설계: 정책 테이블을 TP 벡터로 키잉한다
헤즈업 MCCFR의 정보 집합은 `(좌석, 스트리트, 카드 버킷, 공개 히스토리 전체)`다. 9인에서 공개 히스토리를 그대로 키로 쓰면 정보 집합 수가 폭발한다(Pluribus는 6인에서 수억 개, 12,400 CPU 코어 시간).

TP-GTO는 원래 "TP를 거쳐서만 행동"하는 정책이다. 그래서 **키 자체를 TP 벡터로** 둔다.
```
key = (포지션 그룹, 스트리트, 남은 상대 수 1/2/3+, 공격자 여부,
       hand.equity 분위 단계(합성 레인지 대비), 팟 오즈 단계, SPR 단계,
       [중수 이상] board.adv 단계, [고수] hand.outs 단계)
```
- 키 수는 TP 항목 단계 수의 곱으로 고정된다. 초보 약 10³, 중수 약 10⁴–10⁵, 고수 약 10⁵–10⁶. 테이블 수가 좌석 수에 거의 독립적이다. 9인으로 가도 늘어나는 것은 "포지션 그룹"과 "남은 상대 수" 축뿐이다.
- 같은 키의 다른 히스토리끼리 전략을 공유한다(일반화). 이것이 "조건 둔감"(CHARTER 불변 요구)과 같은 말이다. 둔감해도 되는지는 Gate S(유형 버킷 민감성)가 검사한다.
- 공개 레인지는 E2-4처럼 좌석마다 1326 조합 도달 확률로 추적한다. 각 좌석의 `hand.equity`는 남은 상대 전원의 레인지를 합친 합성 레인지 대비(TP.md §3.1 정의, E1m 결론)다.

## 4. 학습: 자기 대전 + 리그
- 기본은 외부 샘플링 MCCFR(선형 평균, 음의 후회 절단)이다. 키가 TP 벡터라 CFR의 수렴 보장은 사라진다(완전 기억 위반). 대신 E1/E1m처럼 **정확히 풀리는 부분 게임에서 손실을 직접 재서** 근사의 비용을 확인한다.
- 리그(사용자 요구: 정책 간 경쟁으로 블러프·착취·다양한 전략이 나와야 한다):
  1. 주 정책(MCCFR 평균)
  2. 착취자(주 정책 고정, 한 좌석이 최선 응답을 학습 → LBR보다 강한 하한)
  3. 과거 스냅샷 풀(순환 착취 방지)
  4. 페르소나 필드(타이트·루즈·콜링 스테이션 등, Gate Q1)

  주 정책은 매 세대 "착취자에게 잃는 양"이 줄어야 다음 세대로 간다.
- 최종 TP-GTO는 이 과정에서 나온 정책이다. 손으로 쓴 규칙 정책은 기준선·페르소나로만 쓴다(사용자 요구).

## 5. 평가 (다인에는 정확한 착취 가능성이 없다)
| 지표 | 무엇을 보장하나 | 단계 |
|---|---|---|
| 좌석별 LBR(한 좌석만 착취, 나머지는 정책) | 착취 가능성의 하한 | E3– |
| 학습한 착취자의 이득 | 더 강한 하한 | E3– |
| 정확한 부분 게임 앵커(푸시/폴드 N인 ICM, 리버 단일 결정) | 그 범위의 실제 손실 | E3–E5 |
| 리그·페르소나 필드 승률/ROI(신뢰구간) | 실전 성능 | E3– |
| Gate S 민감성 | 조건 둔감 | E3– |

"GTO"라는 말은 정확히 풀린 환경에서만 쓴다(Gate Q). E3 이후 화면 표기는 "근사 균형(하한 x bb/핸드)"이다. 전략 브라우저(#189)도 같은 규칙을 따른다.

## 6. 계산량
- 실측(로컬, 1코어): E2 기준선 MCCFR 49 it/s, E2-4 레인지 추적 16–18 it/s, LBR 600핸드 약 1–2분.
- E3 추정: 좌석 6 × 트리 깊이 증가로 반복당 비용이 E2의 약 5–10배 → 2–4 it/s/코어(순수 파이썬). TP 키 테이블 10⁵에 키당 수십 번 방문이 필요하다고 보면 10⁷ 반복 → 약 30–60 코어·일.
- 선택지:
  1. GitHub Actions 무료 러너(공개 리포, 잡당 6시간, 20 동시): 하루 최대 약 2,000 코어·시간. **E3까지 충분.**
  2. 벡터화: 여러 딜을 numpy 배치로 한 번에 걸어 반복당 파이썬 오버헤드를 나눈다. 의존성 추가 없음, 예상 5–20배.
  3. numba(새 의존성 정당화 필요): 10–50배. 2로 부족할 때만.
  4. RunPod(월 $100 한도): CPU 대량 작업보다 GPU(신경망 가치 근사, E5)에 쓴다(#184 결정).
- 순서: E3-0에서 처리량부터 잰다(E2-2 #179와 같은 방식). 목표는 ≥ 20 it/s/코어(벡터화)이고, 못 미치면 numba ADR을 쓴다.

## 8. 위험
- TP 키가 너무 거칠면 착취당한다: 착취자 이득이 크면 해당 등급의 키에 항목을 추가한다. 추가 순서는 기여도 분석(#134)으로 정한다.
- 레인지 추적의 카드 제거 근사(내 홀카드와 겹치는 상대 조합): 6인 이상에서는 조합 간 상호 제거가 커진다. 앵커 게임에서 오차를 따로 잰다.
- 계산량 추정이 틀릴 수 있다: E3-0 실측 뒤 이 노트를 고친다.
