## 0. 왜, 그리고 무엇이 달라지나

- 현재: 유형별 목표(VPIP·PFR·스트리트별 c-bet 등)는 공개 통계 요약값이고, 유형 안의 분산은 가정이다(population-stats §6 "유형 내 분산을 정량화한 공개 자료는 없다").
- 로그가 생기면: 이 서비스를 쓰는 사람들이 실제로 어떻게 치는지로 유형의 중심과 분산을 **측정**하고, 같은 스타일의 상대를 만들 수 있다. 단 이 서비스는 개인 전용이다(헌장 8번). 사용자는 사실상 소유자 한 명이거나 극소수이므로 §5의 표본 추정이 현실성의 한계를 정한다.
- 이 노트의 모델은 학습 서비스 안에서 **연습 상대의 다양성**을 위한 것이다. 사용자 본인을 흉내 내 착취하는 도구가 아니다(§1의 "저장하지 않는 것" 참고).

## 1. 동의·익명화 (무엇을 저장하지 않는가)

원칙: 스타일 모델은 **행동 통계**만 쓰고, 사람을 가리킬 수 있는 정보와 원시 핸드 이력은 모델 입력 단계에서 버린다.

| 구분 | 저장·사용한다 | 저장하지 않는다 |
|---|---|---|
| 식별 | 무작위 `style_subject_id`(로그 단위로 새로 발급, 계정과 연결 테이블 없음 [가정]) | 이메일, 계정 id, 기기 id, IP, 닉네임 |
| 시간 | 핸드 순서(세션 내 인덱스) | 벽시계 타임스탬프(생활 패턴 노출), 결정 소요 시간 |
| 카드·핸드 | 쇼다운으로 공개된 핸드, 공개 상황의 버킷(§3) | 쇼다운 안 된 개인 홀카드의 원문 이력 |
| 요약 | 플레이어 단위 집계 통계(§2) | 핸드별 전체 시퀀스를 계정에 묶은 형태 |

- **동의**: 로그를 스타일 모델에 쓰려면 사용자가 명시적으로 켜는 옵트인이어야 한다([가정]: 기본 꺼짐). 철회하면 그 `style_subject_id`의 집계와 파생 모델 기여분을 지운다. 이미 학습된 모델에서 한 사람의 기여를 빼는 것은 재학습이 필요하다고 본다(모델 재현은 시드 고정이라 가능, 기록 스키마의 재현성 요구와 맞다).
- **연령·제3자**: 이 서비스는 개인 전용이므로 제3자 사용자 가입을 가정하지 않는다. 가입 사용자가 생기는 순간 이 절은 법적 검토 대상이다(§7 열린 결정 1).
- **상대 봇의 데이터**: 봇과 친 핸드의 봇 행동은 사용자 데이터가 아니다. 모델 입력은 사람 좌석의 결정만이다.
- **외부 공개 금지**: 로그·집계·모델 가중치는 외부에 올리지 않는다(헌장 8번).

## 2. 플레이어 단위 스타일 클러스터

### 2.1 입력 통계 (플레이어당 벡터)

population-stats 표의 유형 구분 뼈대와 같은 통계를 쓴다. 그래야 클러스터를 기존 8유형 목표와 직접 대조할 수 있다.

| 차원 | 정의 | 비고 |
|---|---|---|
| VPIP, PFR, VPIP−PFR | 프리플랍 | 유형 구분의 뼈대 [출처: population-stats §1] |
| 3-bet, fold-to-3-bet | 기회 대비 | 기회 수가 작다 → §5 |
| c-bet 플랍/턴/리버, fold-to-c-bet 플랍/턴 | 기회 대비 | 페르소나 `PersonaParams` 필드와 1:1 |
| 리버 폴드, 리버 블러프 비율 | 기회 대비 | 쇼다운된 것만 블러프 판정 가능 |
| AF, WTSD, W$SD | 포스트플랍 | |
| 사이즈-강도 상관 | 벳 사이즈(팟 비율)와 쇼다운 강도 순위 상관 | 사이즈 텔 [가정: 유형 구분에 쓸지 미검증] |

### 2.2 결측과 수축

기회 수가 적은 통계는 베타 사전분포로 수축한다: `p̂ = (x + a) / (n + a + b)`. 사전분포(a, b)는 해당 통계의 population-stats 유형 평균을 중심으로 `a + b = 20` ([가정]) 로 둔다. 표본이 적은 플레이어가 극단값으로 튀어 가짜 클러스터를 만드는 것을 막기 위함이다.

### 2.3 클러스터링과 클러스터 수 선택

- 방법: 표준화한 벡터에 가우시안 혼합(공분산 대각) 또는 k-means. 둘 다 순수 numpy로 구현 가능하다(새 의존성 없음 원칙). 난수는 명시적 시드의 `Generator`.
- 클러스터 수 k 선택 기준(셋 모두 충족하는 가장 작은 k, 범위 2..8 [가정: 기존 8유형이 상한]):
  1. BIC가 k−1 대비 개선되는 가장 큰 k.
  2. 각 클러스터에 **최소 플레이어 수**(§5의 `m_min`) 이상.
  3. 시드를 바꿔 5번 돌렸을 때 플레이어 배정이 안정적(쌍별 일치도 Rand index ≥ 0.9 [가정]).
- 조건을 못 채우면 k=1(단일 "이 서비스 평균 플레이어")로 두고, 기존 8유형 규칙 봇을 그대로 쓴다. 로그가 모델을 못 만들면 모델을 쓰지 않는 것이 기본값이다.
- 클러스터 이름은 사람이 붙이지 않는다. 가장 가까운 기존 유형(nit/TAG/LAG/…)과의 거리를 병기해 대응만 보인다.

## 3. 공개 상황 조건부 행동 복제 모델

### 3.1 입력 (공개 상황 `s`)
플레이어가 **볼 수 있었던 공개 정보**만 쓴다(기록 스키마 `table_observation` 중 본인 관측과 같은 범위):

- 포지션, 스트리트, 팟 대비 유효 스택(SPR) 버킷, 콜 비용 대비 팟 비율 버킷, 프리플랍 어그레서 여부, 남은 상대 수, 보드 질감 버킷(페어드/모노톤/연결성 3×3 [가정]), 직전 액션 종류와 사이즈 버킷.
- 본인 홀카드는 쓴다면 **강도 버킷**(엔진의 `hand_class`와 같은 정의, 예: 에어/약한 페어/탑페어/세트 이상)으로만 쓴다. 원문 카드는 입력에서 제외한다(§1).
- 클러스터 id `c`를 조건으로 준다: 모델은 `π(a | s, c)`.

### 3.2 출력
- 액션 분포: 폴드/체크/콜/벳·레이즈 사이즈 버킷(봇 메뉴와 같은 액션 공간). 기록 스키마의 `action_space`와 정렬된 확률 벡터.

### 3.3 모델 형태 (단순한 것부터)
1. **표(테이블) 기반**: 키 = (스트리트, 포지션 그룹, 상황 버킷, 강도 버킷), 값 = 클러스터별 액션 빈도(수축 포함). 해석 가능하고, 지금 규칙 봇의 `PersonaParams`로 곧바로 환산된다(예: 클러스터별 c-bet 빈도 → `cbet_flop`).
2. **로지스틱 회귀 / 작은 MLP**: 표가 희소할 때. 입력은 위 버킷의 원-핫. 표본이 §5 최소 크기 미만이면 쓰지 않는다.
- 우선순위는 1이다. 지금 봇이 파라미터 몇 개로 표현되므로, 로그에서 얻은 값을 `PersonaParams`에 채워 넣는 경로가 가장 싸고 검증도 기존 `persona_stats`로 된다.

### 3.4 평가 지표
- **보류(held-out) 로그 로그우도**: 같은 플레이어의 보류 핸드에서 평균 −log π(a_true | s, c). 비교 기준은 (i) 균등 분포, (ii) 유형 무관 평균 정책(k=1). 클러스터 조건이 (ii)보다 개선되지 않으면 클러스터는 쓸모없다.
- **통계 재현 오차**: 모델로 6인 혼합 필드를 시뮬레이션해 §2.1 통계를 측정(`stalker.agents.persona_stats`)하고, 플레이어의 실측과 비교. 기존 페르소나 테스트와 같은 허용 오차(WTSD·c-bet·fold-to-c-bet ±6%p, VPIP·PFR ±5%p)를 출발점으로 한다 [출처: `tests/test_persona_v2.py` 기준].
- **인접 스트리트 지표도 함께 본다**: 플랍·WTSD만 맞추면 턴·리버가 왜곡된다는 지적이 있었다(#533, PR #531 리뷰). 지표 세트에 턴·리버 fold-to-bet을 넣는다.
- 판정 근거는 CI뿐이라는 원칙(CLAUDE.md)은 그대로다. 구현 시 이 지표들은 CI 체크로 만든다.

## 4. field 분리 (#413: 학습·선택·감사 상대 분리)

#413은 학습·선택·감사 상대를 분리하도록 정했다(RL-BR 공격자는 dev/audit 시드 분리, 필드는 `field_v2` 이전 챔피언 포함 [출처: #413, PR #467·#474]). 로그에서 만든 스타일 상대에도 같은 분리를 적용한다.

| 용도 | 쓰는 플레이어(스타일 주체) | 규칙 |
|---|---|---|
| 학습 상대 | 로그 주체의 **학습 분할** | 학습 중 상대 풀에 들어간다 |
| 선택 상대 | **선택 분할**(다른 주체) | 체크포인트 선택·하이퍼파라미터 결정에만 |
| 감사 상대 | **감사 분할**(또 다른 주체, 최종 보고 전까지 열지 않음) | 최종 감사에만. 모델 개발에 못 쓴다 |

- 분할 단위는 **주체(플레이어)**이지 핸드가 아니다. 같은 사람의 핸드가 두 분할에 섞이면 스타일이 새서 감사가 낙관적이 된다.
- 주체 수가 적으면(§5) 3분할이 불가능하다. 이때는 분할을 억지로 만들지 않고, **로그 유래 상대를 감사 필드에 넣지 않는다**(기존 `field_v1`·`field_v2` 유지). 로그 상대는 학습 서비스(연습 상대)에만 쓴다.
- `referee/e3/field_v*.json`은 보호 경로다. 새 필드 파일은 `referee-change` 이슈에서만 만든다(§7).

## 5. 최소 표본 크기 추정

모든 식은 이항 비율의 정규 근사다 [계산]: 95% 신뢰구간 반폭 `h`를 얻으려면 기회 수 `n = 1.96² · p(1−p) / h²`.

### 5.1 플레이어 한 명의 통계를 재는 데 필요한 기회 수 (h = 0.05)

| 통계 | p (가정) | 필요한 기회 수 n [계산] | 기회가 생기는 비율 [가정] | 필요한 핸드 수 |
|---|---|---|---|---|
| VPIP | 0.25 | 1.96²·0.25·0.75/0.05² ≈ **288** | 1.0 | ≈ 288 |
| PFR | 0.18 | 1.96²·0.18·0.82/0.05² ≈ **227** | 1.0 | ≈ 227 |
| c-bet 플랍 | 0.60 | 1.96²·0.6·0.4/0.05² ≈ **369** | 0.12 (PFR 18% × 헤즈업 확률 ≈ 2/3) | ≈ 3,100 |
| fold-to-3-bet | 0.55 | 1.96²·0.55·0.45/0.05² ≈ **380** | 0.01 | ≈ 38,000 |
| 리버 블러프 비율 | 0.30 | 1.96²·0.3·0.7/0.05² ≈ **323** | 0.02 (리버까지 간 어그레서 벳) | ≈ 16,000 |

해석: 프리플랍 총량 통계는 수백 핸드면 되지만, 조건부·희귀 통계는 수만 핸드가 필요하다. 한 명의 사용자가 그만큼 치는 일은 드물다. 그래서 §2.2 수축이 필수이고, 희귀 통계는 클러스터 수준에서 풀링한다.

반폭을 0.10으로 완화하면 필요한 기회 수가 1/4이다(위 표의 n을 4로 나눔) [계산].

### 5.2 클러스터링에 필요한 플레이어 수

- 클러스터당 최소 플레이어 `m_min = 30` ([가정]; 평균·공분산을 대각으로만 추정하는 최소선). 따라서 k개 클러스터에는 **≥ 30k명**이 필요하다 [계산]: k=3이면 90명, k=8이면 240명.
- 현재 사용자는 사실상 1명(헌장 8번 개인 전용)이므로 **플레이어 단위 클러스터링은 지금 불가능**하다. 가능한 것은 (a) 사용자 한 명의 스타일을 본인 연습 기록 분석에 보이는 것, (b) 사람 수가 임계를 넘었을 때를 위한 설계 보존이다. 이 사실이 §7 열린 결정 2의 근거다.

### 5.3 행동 복제 표의 칸당 최소 표본
- 칸 하나의 빈도를 ±0.10(95%)로 추정하려면 p=0.5 최악 기준 n ≈ 1.96²·0.25/0.10² ≈ **96** 결정이 필요하다 [계산]. 키 수가 수천이면 수십만 결정이 필요 → 표 모델은 키를 (스트리트 × 포지션 그룹 × 강도 버킷) 수준(대략 3×3×4 = 36칸 [가정])으로 거칠게 잡아야 사용자 한 명의 로그로도 채워진다(36칸 × 96 ≈ 3,500 결정 [계산]).

## 6. 기록 스키마 (제안만)

현재 기록 스키마는 v2다(`stalker/records/schema.py`, `docs/RECORDS.md`). 스타일 모델에 필요할 수 있는 추가는 아래 **제안**뿐이며, **이 노트는 `schema_version`을 바꾸지 않는다.** 실제 변경은 별도 이슈에서 `schema_version` 상승과 마이그레이션·호환 테스트를 동반해야 한다(CLAUDE.md).

- 필요 없는 것으로 판단: 모델 입력은 기존 `table_observation`(본인 관측)과 `chosen_action`으로 대부분 재구성된다. 새 필드 없이 가능한지 먼저 확인한다.
- 있다면 제안: (i) `style_subject_id`(§1의 무작위 id, 기존 식별자 `player_id`와 별개), (ii) 동의 상태 `style_consent`(옵트인 여부, 철회 시각은 저장하지 않음 §1), (iii) 결정이 사람 좌석인지 봇 좌석인지 구분하는 `actor_kind`(`human`/`bot`).
- 위 필드가 필요해지면 기록 품질 게이트(D5)와 `referee/` 보호 경로 영향을 먼저 확인한다.

## 7. 열린 결정 (기록·개인정보 — 별도 이슈/NH 필요)

이 노트가 정하지 않고 넘기는 것. 코드 작업 전에 반드시 풀려야 한다.

1. **개인정보·동의의 법적 지위**: 개인 전용(소유자 1명)을 넘어 사용자가 생길 때의 동의 문구, 보관 기간, 삭제 요청 처리. 사람만 할 수 있는 결정이므로 `ops:NEEDS_HUMAN.md` 항목(NH) 후보. 막히는 이슈: 로그 수집 구현 이슈 전부.
2. **수집 시작 여부**: §5.2에 따르면 사용자가 한 명이면 클러스터링이 의미 없다. 사용자 수가 얼마 이상일 때 시작할지(제안: 클러스터 수 k 선택 기준 충족 시), 그 전까지는 §3.3의 표 모델로 본인 스타일 분석만 할지.
3. **기록 스키마 변경**: §6 제안을 받아들일지. `schema_version` 상승 이슈로 분리한다.
4. **감사 필드에 로그 상대를 넣는지**: §4에서는 넣지 않기로 했다. 넣는다면 `field_v3`가 필요하며 `referee-change` 이슈와 주체 수 임계 결정이 선행한다.
5. **벽시계 시간·결정 시간 사용 여부**: §1은 저장하지 않는다. 텔 학습(population-stats §5)에 쓸지는 개인정보 비용과 효과를 따로 판단한다.
