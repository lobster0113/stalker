# 데이터 충분성 정체 원인: 게임 수별 곡선 — #89

> **모든 수치는 로컬 실행값, 참고용이다.** 판정 근거가 아니다(CHARTER: 근거는 CI뿐).

## 질문
CI 충분성 지표(sng6 100게임, 시드 1)가 `suff_lessonable_cells` 0/1317, `suff_s1_rate` 0.0, `d1_preliminary` 0.0에서 움직이지 않는다. 원인이 표본 수인가, 셀 과분할인가, 기준(S1 rule-of-three)인가? D1 ≥ 95%에는 데이터가 얼마나 필요한가?

## 방법
- 재현: `python scripts/sufficiency_curve.py --games 100,300,1000 --seed 1 --out DIR` → `DIR/curve.json`.
- 참조 봇 sng6 1000게임을 한 번 생성한다. 게임 i의 시드가 `[seed, i]`라서 앞 k게임은 k게임 데이터셋과 같다. 따라서 100게임 지점은 CI 지표와 같은 데이터다(셀 1317, S4 0.185, S5 0.046로 CI 값과 일치). 지점마다 `build_report`(심판 `judge_cell`의 S1/S4/S5)를 다시 돌린다.
- 외삽 모델(`required_games`): 셀마다 게임 클러스터 표준오차(se)를 구하고, se가 1/√(셀이 나온 게임 수)로 준다고 가정한다. 다음 두 조건을 모두 만족하는 게임 수를 셀의 필요량으로 둔다.
  - rule-of-three: 각 절반이 60토너먼트 이상(3/n ≤ 0.05). 따라서 셀 출현율 f에서 120/f 게임.
  - 분산: 절반 se ≤ 0.0180. S1(z·se ≤ 0.05), S4(z·√2·se ≤ 0.05), S5(z·√(1/0.8−1)·se ≤ 0.02) 중 가장 엄한 S4 값이다.
  - 이 필요량을 결정 비율로 누적해 D1 도달 게임 수를 낸다. 모델은 S4 주 액션 일치 조건(근소한 동률)과 아직 안 나온 셀을 무시한다.

## 결론과 다음 행동
1. **정체의 1차 원인은 CI 데이터셋 크기다. 셀 분할이나 기준 자체가 아니다.** 100게임이면 각 절반에 많아야 50토너먼트가 들어간다. 그러면 S1 rule-of-three 하한이 3/50 = 0.06 > 0.05라서 **어떤 셀도 S1을 통과할 수 없다**. 실제로 100게임 상위 20개 셀의 최대 반폭은 모두 0.060 이상이다(상위 9개는 0.060~0.069). S1을 통과할 수 있는 최소 크기는 120게임(절반당 60)이다. 300게임이면 D1 0.21, 1000게임이면 0.54로 움직인다. 지금 지표 0.0은 "데이터가 모자라다"는 정보만 줄 뿐 진척을 측정하지 못한다.
   - **후속 이슈 제안 (referee-change, P1)**: `SUFFICIENCY_GAMES`를 100에서 300 이상으로 올린다. 이 머신 기준 생성 8분, 리포트 12초라 record-metrics 30분 한도 안에 든다. 추세 단절은 metrics에 표시한다. 이 결정은 CI 데이터셋 크기 변경이라 이 이슈의 범위 밖이다.
2. **D1 95%에는 약 3.5만~4.2만 게임(sng6, 약 700만~800만 결정)이 필요하다.** 모델이 보수적이라 실제로는 이보다 적을 것이다. D1 99%는 16만~46만 게임으로 꼬리 셀이 지배한다. 근거: 위 외삽표와 1000게임 실측 대비 과소 예측.
   - **후속 이슈 제안 (P2)**: 3000·10000게임 지점을 실측해 외삽을 검증한다. 배치 실행이 필요하다(아래 3).
3. **셀 병합/분할 규칙: 고정 분할이 DATA_SUFFICIENCY.md 원칙 3("두 자식이 모두 통과할 때만 분할")과 어긋난다.** 1000게임에서 셀 2,269개 중 약 절반이 적은 쪽 절반에서 3게임 이하다. 셀 수는 게임 수와 함께 계속 늘어난다(1317 → 1765 → 2269). 이 꼬리가 95% → 99% 구간의 필요량을 4~13배로 키운다. 반면 결정 비율로 보면 상위 셀이 빨리 채워진다(1000게임에서 72셀 = 결정 54%).
   - **후속 이슈 제안 (P2, area:typing)**: 계층 백오프 유형화. 미달 셀은 상대 프로파일 → 스택 구간 → 단계 순으로 부모 셀에 합친다. 부모와 자식이 모두 통과할 때만 분리해 표시한다. 같은 데이터에서 D1이 얼마나 오르는지 이 스크립트로 비교한다.
   - #90(생성 우선순위)은 이 결과와 맞물린다. 미달 셀의 대부분이 "출현 드문 꼬리"라서, 출현 빈도 가중 우선순위가 생성 효율을 크게 바꿀 것이다.
4. **생성 비용은 클라우드 VM 배치로 감당할 수 있다.** 결정당 약 8.5 ms(1코어)이므로 D1 95%의 4.2만 게임은 약 19 CPU-시간이다. 16코어 VM이면 1.2시간이다. D1 99%의 16만~46만 게임은 70~200 CPU-시간이다. GPU는 필요 없다(참조 봇 기준. 신경망 AI는 결정당 비용을 다시 재야 한다).
   - **막히는 점**: `build_report`가 모든 결정을 메모리에 올린다. 1000게임에 결정 19만 개이므로 4.2만 게임이면 약 800만 개라 한 프로세스에서는 무겁다. `generate`도 게임 범위를 나눠 병렬로 돌릴 수 없다(항상 0번 게임부터).
   - **후속 이슈 제안 (P2, area:records)**: `generate --start/--count` 샤딩과 리포트용 셀별 스트리밍 집계를 추가한다. 배치 실행 자원은 NH-1 결정(클라우드)과 엮인다. CPU VM만으로 충분하다는 근거를 NH-1에 덧붙인다.
