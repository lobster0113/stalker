## 선택
**M4 (원본 run 41813684540, 시드 4), `export_strategy=current`, `min_visits` = 10.**

### 시드: M4
1. **합격선**: 세 run 모두 ADR 0020의 인원별 현재 LBR 선 5개를 다 통과한다(위 표). 평균 전략 선도 모두 통과한다. 그래서 세 run 모두 후보다.
2. **최악 인원 LBR**: 각 run에서 가장 큰 `lbr_bb`는 셋 다 2인이다. 그 값이 M2 7.077, M3 7.309, **M4 7.018**로 M4가 가장 낮다. 이슈 기준(「최악 인원 LBR이 가장 낮은 것」)에 따라 M4를 고른다. 동률이 아니므로 키 수 비교는 쓰지 않는다.
3. **한계**: 1위 M4와 2위 M2의 차이는 0.06이고, 2인 평가 se(약 0.94)의 1/15이다. 이 차이로 시드 품질을 구별할 수는 없다. 기준을 기계적으로 적용한 결과일 뿐이다. ADR 0020은 인원별 LBR의 척도가 다르다고 적는다. 그래서 참고로 인원별 `lbr_bb / 선`의 최댓값으로도 비교했다. M2는 0.918(4인), M3는 0.812(2인), M4는 0.904(6인)이고, 이 기준이면 M3가 고르게 여유가 크다. M4는 6인이 2.440으로 선 2.7에 0.26 차까지 가 있다. 평균 전략으로 보면 M4는 3인이 4.887로 선 5.2에 0.31 차(`lbr/선` 0.94)까지 가 있어 세 run 15개 값 중 가장 빠듯하다(M2 최댓값 0.849, M3 0.839). 즉 M4는 현재 전략 6인 0.904와 평균 전략 3인 0.94 두 곳에서 여유가 가장 작다. 6인·3인을 주로 쓰는 화면에서 이 점이 문제가 되면 M3로 바꾸는 것을 「후속」에 남긴다.

### `min_visits` 문턱: 10 (추정)
15개 파일이 모두 3MB를 넘으므로 문턱이 필요하다. 요약에는 문턱별 **키 수**만 있고 문턱별 **바이트**는 없다. 그래서 바이트는 「추정」이다. 추정식은 `bytes(t) ≈ keys(t) × (bytes / keys)@min_visits=0`이다. 키당 바이트는 M4 기준 2인 76.9, 3인 74.7, 4인 72.3, 5인 69.9, 6인 68.9다. 키당 길이가 문턱과 무관하다고 가정한다. 이 가정은 검증하지 않았다.

M4에서 인원별로 3MB를 통과하는 가장 작은 문턱(추정):

| 인원 | 문턱 | 남는 키 | 추정 바이트 | 바로 아래 문턱의 추정 바이트 |
|---|---|---|---|---|
| 2 | 10 | 18,413 | ≈ 1.42MB | 5 → 42,038키 ≈ 3.23MB (상한 3.15MB 초과) |
| 3 | 5 | 36,032 | ≈ 2.69MB | 2 → 120,243키 ≈ 8.98MB |
| 4 | 5 | 20,443 | ≈ 1.48MB | 2 → 84,493키 ≈ 6.11MB |
| 5 | 5 | 11,361 | ≈ 0.79MB | 2 → 55,645키 ≈ 3.89MB |
| 6 | 2 | 39,155 | ≈ 2.70MB | 1 → 170,771키 = 11.76MB (실측) |

M2·M3도 인원별 최소 문턱이 같다(2인 10, 3–5인 5, 6인 2). 다만 M3 6인 문턱 2는 39,108키 ≈ 2.69MB로 상한 가까이 간다.

`cloud.yml` `export_min_visits`는 run 전체에 값 하나만 받는다. **모든 인원을 한 번에 통과시키는 가장 작은 단일 문턱은 10**이다. 2인 기준이 문턱을 결정한다. 문턱 10에서 M4가 남기는 키는 2–6인 18,413 / 14,980 / 7,567 / 3,795 / 2,496이다. 5–6인은 키가 2–4천 개로 줄어 정책 표의 대부분이 기본 전략으로 넘어간다. 인원별 문턱(2인 10, 3–5인 5, 6인 2)을 쓰면 6인 키가 39,155개로 약 16배 많다. 이렇게 하려면 export가 인원별 문턱을 받아야 한다(「후속」 2).

문턱을 거르면 서비스 정책은 LBR을 잰 정책과 달라진다. 위 표의 LBR은 거르기 **전** 정책의 값이고, 걸러 낸 정책의 LBR은 아직 아무도 재지 않았다(「후속」 3).

## mid-6 적중률 비교 (#620)

**참고용(로컬) 수치** — CI 수치가 아니다. `web_hit_rate`에 `--variant`(기본 auto: 파일의 `key_variant`, 없으면 첫 비-`call|` 키로 판별)를 더해 레거시(c1 이전) 키 표도 잰다. 레거시는 페이지가 조회하는 키(`tpgto.js decisionKey` variant `""`: 좌석 번호 키, `publicKey`·`equitySteps`)와 같은 `tp_key` 함수(variant `""`)로 만든다. 레거시 표는 `--backoff`를 지원하지 않는다(거친 키 수준이 c1 키 모양에 묶여 있음).

```
python -m stalker.tools.web_hit_rate web/app/policy/mid-6.json --hands 2000 --seed 620                  # 레거시(커밋된 파일, v1 메뉴·캡 3)
python -m stalker.tools.web_hit_rate <ops:cloud/policies/41813684540/mid-6.json> --hands 2000 --seed 620 --backoff   # c1(ops 68a3dd5d, real 메뉴)
```

각 표는 자기 파일의 규칙(`rules_of`)으로 같은 시드·6인 2000핸드를 돈다. 메뉴가 달라 두 표의 결정 수와 상황 분포는 같지 않다(레거시 17,988·c1 18,928 결정).

## 백오프 플레이 적중률 (#635)

**참고용(로컬) 수치** — CI 수치가 아니다. `web_hit_rate --play-backoff`(`--backoff` 포함)는 정밀 키 미적중 때 페이지(`tpgto.js backoffRow`, #623)처럼 L1 → L2 → 균등 순으로 행을 골라 행동하고 범위도 그 행으로 갱신한다. 켜지 않으면 출력은 그대로이고, 켜면 `"play": "backoff"`·`schema_version` 3이 붙는다. 수준별 결정 수는 그 궤적에서 센다.

```
python -m stalker.tools.web_hit_rate <ops:cloud/policies/41813684540/mid-6.json> --hands 2000 --seed 620 --backoff        # 균등 플레이
python -m stalker.tools.web_hit_rate <같은 파일> --hands 2000 --seed 620 --play-backoff                                  # 페이지와 같은 플레이
python -m stalker.tools.web_hit_rate web/app/policy/mid-{2..5}.json --hands 2000 --seed 620 --play-backoff                # 커밋된 표
```

- 시간 제약: 원본 체크포인트 아티팩트는 ~12-03에 만료된다. 플랍 커버리지를 올리려면 만료 전에 플랍 키 커버리지를 늘리는 학습·문턱 변경(#631 등)이 필요하며, 이 노트는 교체하지 않는다.

## L2 미적중 원인 (#638)

**참고용(로컬) 수치** — CI 수치가 아니다. `web_hit_rate --play-backoff --miss-report N`은 페이지 규칙(L1 → L2 → 균등)으로 플레이하면서 L2 뒤에도 균등인 결정을 스트리트별로 L2 키 단위로 세고(상위 N), 같은 결정의 L2 키에서 **필드 하나만** `*`로 바꿨을 때 L2 표에 같은 길이의 행이 생기는지를 필드 위치별로 센다(`by_field`, `any_field` = 하나라도). 플레이는 바뀌지 않고(테스트로 단언) 출력에 `"miss_report"`·`schema_version` 4가 붙는다. 끄면 출력 바이트가 그대로다.

```
python -m stalker.tools.web_hit_rate web/app/policy/mid-{2..5}.json --hands 2000 --seed 620 --play-backoff --miss-report 10
python -m stalker.tools.web_hit_rate <ops:cloud/policies/41813684540/mid-6.json> --hands 2000 --seed 620 --play-backoff --miss-report 10
```

코드·커밋된 표는 main ee86d09e, mid-6은 `ops` 커밋 5b5f2875의 파일(sha256 c02843ca…, 위 대조값과 같음).

L4가 3·4·6인(과 교체 전 2인 파일)에서 플랍 균등을 5%p 이상(6.2–10.7%p) 줄인다(5인 3.5%p, 현재 2인 mv=5 파일 3.4%p) → 이슈의 문턱(어느 인원이든 5%p 이상)을 넘는다. `tpgto.js backoffRow`에 같은 L4(L3 표에서 에퀴티 ±1 이웃 평균)를 미러하고 ADR 0022에 수준을 더하는 후속 이슈를 추천한다. 조건 둔감 근거: 에퀴티 칸은 자기 패와 공개 보드(와 공개 행동으로 갱신한 범위)로만 정해지고, 근사 행은 채점에서 빠진다. 5인은 L4로도 해결되지 않으므로 커버리지 학습(#629)은 별도 레버로 남는다.

JS 미러 완료 (#652): `tpgto.js backoffRow`가 같은 L4를 찾고 ADR 0022 「갱신 (#652)」에 수준을 더했다.

## 백오프 결합 방식 (#660)

**참고용(로컬) 수치** — CI 수치가 아니다. #654의 원인 추정("순수에 가까운 행들의 **평균**이 균등 비슷한 혼합이 된다")을 검증하려고 `backoff_fidelity`에 `--combine mode`(거친 칸의 leave-one-out 행들 중 argmax가 가장 많은 액션을 고르고 그 액션을 argmax로 갖는 행들만 평균, 동률은 가장 작은 인덱스; L4는 이웃 칸 각각의 mode 행을 같은 규칙으로 다시 결합)와 칸별 `argmax_agree`(근사 행 argmax = 정확 행 argmax인 키 비율, 균등 근사는 1/m로 셈)·`uniform_argmax_agree`(1/m 평균)를 더했다(출력 `schema_version` 2, `--combine mean`의 기존 필드 값은 그대로 — #654 표와 같은 수).

```
python -m stalker.tools.backoff_fidelity web/app/policy/mid-{2..5}.json --l4-neighbor --combine {mean,mode}
python -m stalker.tools.backoff_fidelity <ops:cloud/policies/41813684540/mid-6.json> --l4-neighbor --combine {mean,mode}
```

코드는 main ee7a35fb + 이 PR. 표 파일은 #654와 같다: sha256 mid-2 66613749… · mid-3 c78a3259… · mid-4 3f248f0c… · mid-5 0b785199… · mid-6 c02843ca…(ops 커밋 5b5f2875). 한 칸 = `n` · `tv_mean` / `uniform_tv_mean` · `argmax_agree` / `uniform_argmax_agree`. **굵게** = 유지 기준(`tv_mean` < `uniform_tv_mean` **또는** `argmax_agree` ≥ `uniform_argmax_agree` + 0.10) 충족. 비-`call|` 키.

| L4 | 8/20 (1 / 8), 키 1,406/3,726 | 4/20 (0 / 4), 키 516 |

mode가 mean보다 `tv_mean`이 작은 칸은 79개 중 1개, `argmax_agree`가 높은 칸은 25개(대부분 ±3%p 안)다. `call|` 키는 두 방식 모두 L2 `tv_mean` 0.15–0.21 대 균등 0.32–0.37, `argmax_agree` 75–89% 대 50%로 기준 충족(mode가 나은 점 없음).

읽는 법:
- **추정은 틀렸다.** 평균 행은 TV로는 균등과 비슷하지만 argmax는 균등보다 자주 맞힌다(L1 플랍 40–45% 대 28–40%, +3–13%p). 다수결 행은 TV가 모든 칸에서 커지고(L1 플랍 +0.025~+0.049) argmax 일치도 같거나 낮다. 즉 거친 칸 안의 행들은 "argmax가 갈린 순수 행 두 무리"가 아니라 정말로 행동이 다른 키들이 섞인 것이고, 다수결은 소수 쪽 키를 완전히 틀리게 만든다.
- 평균 행의 가치는 분포가 아니라 **가장 그럴듯한 액션 순위**에 있다: TV 조건만으로는 L1도 7/20칸이지만 argmax 조건으로는 12/20칸이다.
- 같은 한계(#654 「한계」 1–3)가 그대로 적용된다: 정확 키 분포(키당 1표)이지 플레이 미적중 분포가 아니고, 같은 길이 m의 행만 결합하며, TV·argmax는 EV 손실이 아니다.

### 추천

- **(a) 결합 방식: mean 유지.** mode는 TV에서 79칸 중 78칸 나쁘고 argmax 일치에서도 이기지 못한다. 페이지(`tpgto.js` `backoffRow`)·ADR 0022의 평균 규칙을 바꿀 근거가 없다.
- **(b) 수준별(mean 기준)**: L1 **유지**(20칸 중 12칸, 키 75%가 기준 충족; 나머지도 TV 차 +0.05 안). L2 **유지**(11/19칸, 특히 4·5인과 프리플랍·리버; `call|` L2는 확실히 유지). L3 **조건부 유지**(10/20칸, 4인·리버에서 강함, 나머지는 균등과 비슷 — 남겨도 손해가 작다). L4 **제거 후보**(8/20칸, TV 조건은 2인 리버 1칸뿐이고 플랍은 2인 말고 모두, 턴은 모든 인원 미달; 충족 칸은 2인 플랍·리버 2·3·4·6인·프리플랍 2·4·5인). #654의 "L2·L3 제거 후보"는 argmax 일치를 보면 너무 강했다.
- **(c) 반영**: `tpgto.js`·`web_hit_rate.neighbor_row`에서 L4를 끄는 것(또는 L4 미적중을 균등으로)만 후보이며, 그 전에 플레이 가중(`web_hit_rate --play-backoff` 궤적에서 정확 키를 가린 TV·argmax) 측정으로 확인하는 Planner 후속 이슈를 제안한다. 결합 방식(mean)·L1–L3는 바꾸지 않는다.

### 추천

- **(a) L4**: 이 측정으로는 **끄는 쪽도 유지하는 쪽도 증거가 약하다** — 플레이에서 L4에 닿는 결정이 52/약 28,000건(0.2%)이고 기준 충족 칸은 5인 프리플랍 하나다. 끄면 영향이 극히 작고(해당 결정이 균등으로 바뀜), 켜 둬도 플레이에 미치는 영향이 극히 작다. 인원별: 2인 L4 0건, 3·4·6인 균등보다 나쁨(n ≤ 22), 5인 argmax만 충족. 따라서 **끄기 후보 유지, 급하지 않음**(코드 단순화 이점 말고 성능 근거 없음).
- **(b) L3**: 플레이에서 12건뿐이라 **판단 불가 → 현행 유지**(남겨도 손해가 없다). #660의 "조건부 유지"를 바꿀 자료가 아니다.
- **(c) 끄기로 결정하면 바꿀 곳**: `tpgto.js backoffRow`의 L4 단계, `web_hit_rate.neighbor_row`·`--l4-neighbor`, ADR 0022 본문 — 반영은 Planner 후속.
